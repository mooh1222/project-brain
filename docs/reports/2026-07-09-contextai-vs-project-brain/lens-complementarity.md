## 한 줄 결론

두 도구는 **경쟁 관계가 아니라 서로 다른 문제를 푼다.** ContextAI는 "이미 여러 곳에 흩어져 있는 팀·타서비스 지식을 실시간으로 끌어와 권한 걸러 보여주는" 도구이고, project-brain은 "우리 프로젝트에서 무엇을 결정하고 무엇을 배웠는지를 증류·검수해 쌓아두고 코딩 루프 안에서 회상하는" 도구다. 그래서 "품질이 밀리지 않으면 로컬을 계속 쓴다"는 판단은 **타당하지만, 판단의 근거를 '품질 비교'에 두는 것 자체가 틀린 축**이다. 품질이 설령 ContextAI가 더 좋아도 그게 project-brain의 일을 대신하지 못하기 때문이다. 아래에서 근거를 편다.

---

## 1. 두 시스템이 실제로 푸는 문제 — 보완성 3렌즈

### (1) 데이터 모델 — 이게 가장 깊고, 억지가 아니라 진짜로 갈린다

**project-brain은 "증류된 지식"을 만든다.** 결정(DecisionRecord)·교훈/위험(Insight)·용어(GlossaryTerm)·코드↔기획 매핑(DomainMapping) 같은 19종 객체를, candidate→reviewed 검수 사다리를 태워 `brain/<kind>/id.json`으로 쌓는다(보고서 G). 이건 **어느 원본 소스에도 원래는 없던 2차 산물**이다. 출발점 자체가 "RAG는 매번 새로 찾고 아무것도 안 쌓인다 → 누적되는 구조화 산물을 유지하라"였다(design-canonical.md).

**ContextAI는 "원본 소스를 실시간으로 끌어와 조각을 회수"한다.** 소스는 Confluence 위키·붙여넣기 텍스트·Jira(색인형)와 GHE 코드·로그·메트릭(런타임형)뿐이고(보고서 A·D·E), **결정/인사이트/용어를 증류해 만든 검수 객체 타입이 존재하지 않는다.** Binder의 "큐레이션"이라는 것도 "이 서비스가 무엇을 봐야 하는가 = 소스 집합의 선택"이지, "우리가 무엇을 배웠나 = 지식의 증류"가 아니다(보고서 F의 포지셔닝: "커넥터는 파이프, Binder는 큐레이션").

정리하면 두 데이터 모델은 방향이 직교한다.
- **project-brain: 없던 지식을 제조한다(증류·검수·누적).**
- **ContextAI: 이미 있는 지식을 연합·회수한다(federate + retrieve).**

여기가 가장 강한 보완성 지점이다. ContextAI에는 DecisionRecord/Insight/GlossaryTerm에 해당하는 1급 타입이 없고, project-brain에는 Confluence/Jira/라이브 소스 커넥터가 없다.

**단, 겹치는 지점은 겹친다고 말해야 한다.** 팀이 결정·용어를 Confluence에 글로 써 두면 ContextAI는 그걸 회수한다. "용어 X가 뭐냐"는 질문은 답이 소스에 있으면 둘 다 답한다. 차이는 충실도다 — project-brain의 GlossaryTerm은 검수·중복제거·동의어까지 붙어 앵커 게이트에 쓰이는 정제 객체이고, ContextAI는 해당 위키 페이지 원문 조각을 그대로 던진다.

### (2) 소비 지점 — 여기가 유일하게 실제로 부딪칠 수 있는 곳

- **project-brain**: 코딩 에이전트가 **로컬 코딩 루프 안에서** CLI로 회상한다. 서버·데몬 없음, 로컬 git 추적 데이터, 지연은 로컬(보고서 G). "나는 너에게 묻고 너(에이전트)가 CLI를 쓴다"는 모델.
- **ContextAI**: 웹 chat, Query API, 그리고 외부 Flava MCP Hub 경유 MCP export(보고서 B·E). MCP export는 Claude Code·Cursor 등 7종 코딩 에이전트 설정을 만들어 주는 걸 명시적으로 노린다.

**그래서 소비 지점에는 진짜 겹침이 있다.** 둘 다 결국 "코딩 에이전트의 회상 도구" 슬롯을 노린다. 하지만 현재로선 겹침이 얕다.
- ContextAI의 MCP 종단(서버)은 **이 저장소 밖 별도 Hub**이고 현재 릴리즈에서 비활성/게이트 상태다(보고서 B). 위키상으로도 "현재 인증 없음, public 바인더만"(보고서 F).
- 무엇보다 **ContextAI에는 로컬 작업 디렉토리를 가리키는 소스가 아예 없다**(보고서 E). 지식 주입은 텍스트를 건당 5만 자 붙여넣거나 레포를 도달 가능한 Git 원격에 올리는 것뿐. 즉 "내 로컬 코드베이스를 실시간으로 물려 코딩 중에 질의"하는 project-brain의 핵심 루프를 **구조적으로 못 한다.**

### (3) 신뢰 모델 — 축이 다르다(부분 겹침)

- **project-brain의 신뢰 = 인식론적 신뢰.** "이 지식이 검수됐나(reviewed vs candidate), 근거가 뭔가(source_object_ids/evidence_refs), 원문 공개 승인됐나(redaction_status, fail-closed)." **단일 사용자 전제** — 스키마에 acl/sensitivity가 있으나 router가 안 읽어 사용자별 권한은 실집행 안 됨(보고서 G, grep 0건).
- **ContextAI의 신뢰 = 접근 신뢰 + grounding.** 조회자 본인 PAT로 질의 시점에 Confluence/GHE 접근권을 확인해 못 보는 콘텐츠는 LLM에 아예 안 보냄(fail-closed, 보고서 B). **다중 사용자·역할 모델**이 핵심. 반대로 **검수 사다리·증류 객체 개념은 없다.**

두 신뢰 축은 서로 대체가 아니라 보완이다. project-brain의 "검수 상태"에 대응하는 게 ContextAI엔 없고, ContextAI의 "사용자별 열람 권한"에 대응하는 게 project-brain엔 없다(애초에 1인용). 겹치는 건 **환각 억제**뿐이다 — project-brain의 답변 게이트("근거 없으면 없다") + needs_clarification과 ContextAI의 LLM 관련성 필터(fail-closed drop) + no-result 가이던스는 **독립적으로 도달한 수렴 해법**이다.

## 2. Q1 — ContextAI 실사용 평가

**엔지니어링 규율은 성숙하다.** ADR 17건, 계약 우선(코드>테스트>자연어), invariant 테스트, spec-driven 파이프라인, 촘촘한 Prometheus 지표(보고서 C·D). 위키상 이미 사내 정식 오픈(5/12)·MCP export(6/10)까지 나갔다(보고서 F).

**그러나 실사용 관점에서 개인 개발자에게 걸리는 지점이 뚜렷하다.**
- **개인 턴키 도구가 아니다.** 사내 k8s 호스팅 서비스이고 CorporateIdP·FCP·Athenz·사내 OpenAI egress·GHE App·사내 PostgreSQL이 전제(보고서 E). 셀프호스트는 개발용 stack뿐, 실제 답변 생성 로컬 단독 실행 불가.
- **로컬 프로젝트 지식 주입 경로가 없다.** 위 (2)에서 말한 대로. 이 도구의 자연스러운 결은 "Confluence·GHE에 이미 있는 팀 지식을 binder로 묶어 회수"이지 "내 로컬 코드를 실시간으로 물리기"가 아니다(보고서 E 결론).
- **한국어 본문 검색에 구조적 리스크.** 형태소 분석기 없음, 본문 대상 BM25/전문검색 없음. 어휘 매칭(identity)은 제목/경로/id 메타에만 LIKE로 걸리고 **본문에만 있는 희귀 한국어 용어는 dense recall에 전적으로 의존**(보고서 A). Jira는 dense 단독, 소스 간 병합은 관련도가 아니라 우선순위+신선도 정렬.
- **검색 품질을 재현 가능하게 측정하지 않는다.** 과거 커밋되던 골든셋 A~E 평가를 2026-05-15에 통째 삭제했고, "질의에 올바른 문서가 상위로 오는가"를 못 박는 결정론적 테스트가 없다(보고서 C). 즉 ContextAI 팀조차 자기 검색 관련성 수치를 저장소에서 못 댄다.
- **지속성 리스크.** 커밋 ~92%가 1인(보고서 C).
- **제품의 진짜 목표가 개인 코딩 루프가 아니다.** "여러 AI 실행 계층이 공유하는 재사용 문맥(Binder) 인프라"가 되는 것이고, 성공 지표를 chat 사용량이 아니라 "Binder 재사용 단위 채택"으로 잡았다(보고서 D·F).

## 3. Q2 — 벤치마킹: 가져올 것 / 안 가져올 것

### 가져올 만한 것(ContextAI가 실제로 앞서거나 흥미로운 지점)
- **heading 단위 위키 청킹 + breadcrumb + 섹션 앵커 딥링크 인용**(보고서 A). 페이지가 아니라 섹션으로 점프하는 인용 정밀도. project-brain 인용 모델은 보고서 G에 깊이 안 나와 있어 **직접 비교는 근거 부족**이지만, 기법 자체는 구체적이고 이식 검토 가치가 있다.
- **증분 재색인**(content_hash manifest, 안 바뀐 페이지 재임베딩 없이 복사, 보고서 A). project-brain은 전체 재구축만 존재(보고서 G). 다만 코퍼스가 작으면 이득이 작을 수 있어 우선순위는 낮다.
- **LLM 관련성 필터를 검색 위 정밀도 패스로**(fail-closed drop, 보고서 A·B). project-brain엔 앵커 게이트는 있어도 문서별 LLM keep/drop은 없다. **단 비용·지연·recall 삭감 리스크**가 명시돼 있어(보고서 A·C) 무조건 좋은 건 아니다.
- **실트래픽 LLM 심사관 + 트리아지 UI + 데이터 기반 개선 루프**(100트레이스 분석→프롬프트 수정, 보고서 C). project-brain은 골든셋 eval 위주. 사후·정성 신호를 체계적으로 모으는 발상은 배울 만하다.
- **프롬프트 인젝션 경계 처리**(소스 결과 = 지시가 아니라 증거, 보고서 B). grounding 프롬프트 하드닝.
- **다중 사용자 질의 시점 권한 모델**(보고서 B). project-brain의 1번 약점(보고서 G). **단 이건 project-brain이 팀 규모로 갈 때만 의미** — 개인 사용엔 불필요.

### 안 가져올 것(ContextAI가 오히려 약하거나 방향이 다른 것)
- **커밋되는 품질 베이스라인 폐기**(보고서 C가 스스로 꼽은 최대 미결). project-brain의 골든셋 + 556개 결정론 합성 테스트는 오히려 이 축에서 앞서 있다. 따라 하면 퇴보.
- **형태소 없는 한국어 처리 / 본문 BM25 부재.** project-brain의 mecab-ko/kiwi + 색인·검색 토큰화 공유 + 명부 인식 앵커 게이트가 한국어 본문에서 명백히 우위(보고서 A vs G).

## 4. Q3 — "품질 안 밀리면 로컬 유지" 판단은 타당한가

**결론: 타당하다. 단 판단 축을 바꿔야 한다.** 이건 "품질 비교"로 결정할 문제가 아니다.

이유를 근거로 편다.
1. **ContextAI는 project-brain의 핵심 일을 구조적으로 못 한다.** 로컬 작업 디렉토리 실시간 물리기 불가, 미리 구축된 binder + 사내 신원 전제, 서버 호스팅(보고서 E). 그래서 설령 ContextAI 검색 품질이 더 좋아도 "코딩 루프 안에서 이 프로젝트의 증류된 지식을 회상"하는 슬롯을 대신하지 못한다. **품질 우열과 무관하게 대체 불가.**
2. **데이터 모델이 직교한다.** 갈아타면 증류·검수 층(결정/인사이트/용어)이 통째로 사라진다 — ContextAI가 그걸 만들지 않으니까(보고서 A·D).
3. **한국어 본문 검색은 project-brain이 오히려 강하다**(보고서 A·G).
4. **ContextAI가 이기는 지점 대부분은 1인 로컬 도구엔 무관하거나(권한·멀티테넌시), 갈아타지 않고도 흡수 가능한 개선**(섹션 앵커 인용·증분 색인)이다.

그래서 올바른 결정 프레이밍은 **"둘 중 뭐가 낫나"가 아니라 "각자 어느 일을 하나"**다. 개인의 로컬 코딩 루프 + 증류 지식 회상은 project-brain을 유지하고, 팀 전체 Confluence/GHE/Jira 문맥을 같은 에이전트로 끌어오고 싶을 때 ContextAI(또는 그 Binder/MCP)를 **보완 채널**로 붙이는 게 맞다.

**주의 하나** — 회사가 ContextAI를 표준으로 강제하느냐는 조직·정책 축이고, 이 보고서들의 범위 밖이다. 기술적 공존 논거는 강하지만, "개인 도구를 계속 써도 되는가"의 조직적 허용 여부는 보고서로 답할 수 없다.

## 5. 공존 시나리오 — 억지가 아닌 이유

한 코딩 에이전트가 **두 도구를 동시에** 가질 수 있다.
- **project-brain**: "우리가 이 프로젝트에서 무엇을 결정/학습했나"(증류·로컬·검수).
- **ContextAI**: "내가 관리 안 하는 다른 팀 서비스·위키·코드가 뭐라 하나"(연합·라이브·권한).

이 경계선은 내가 지어낸 게 아니라 **ContextAI 자신의 전략 문서가 긋는 선과 정확히 일치**한다 — "내 저장소 탐색은 Claude Code/Codex가 낫고, ContextAI는 내가 관리하지 않는 다른 팀 서비스 맥락에 쓴다"(보고서 D, use-cases.md). 그래서 공존은 억지 정당화가 아니다.

**진짜 겹치는 부분은 솔직히 겹친다.**
- **코딩 에이전트 소비 슬롯**: ContextAI MCP export가 성숙하고 당신 프로젝트의 Confluence+GHE로 binder를 만들면 "프로젝트 문서/코드 회수"에서 실제 겹친다. 하지만 그때도 **증류 객체(결정/인사이트)는 재현 안 된다.**
- **환각 억제**: grounding·fail-closed는 수렴.
- **하이브리드 검색 + RRF**: 같은 계열. project-brain은 그래프 재정렬·한국어 형태소·명부 게이트를 더하고, ContextAI는 LLM 필터·권한을 더한다.

**전략 함의**: ContextAI 로드맵이 "모든 AI 실행 계층의 문맥 레이어"로 커지면(MCP export + 서비스 계정 + 자동 큐레이션), "코딩 루프 내 프로젝트 문맥 회수"에서 겹침이 커진다. project-brain의 지속 가능한 해자는 **검색 기법이 아니라 증류·검수·누적**이다. 그러니 원본 소스 회수 범위로 경쟁하지 말고, ContextAI가 구조적으로 안 하는 "검수된 결정/인사이트/용어의 누적"에 더 힘을 싣는 게 방어에 유리하다.

## 6. 근거의 한계 (보고서가 확립하지 못한 것)

- **양쪽을 같은 질의로 돌린 정면 품질 벤치마크가 없다.** 그래서 사용자의 전제 "품질이 밀리지 않으면"은 **이 보고서들로는 실증 불가**다. 게다가 ContextAI는 결정론적 검색 관련성 테스트 자체가 없어(보고서 C) 비교 기준선이 없다. 판단은 품질 수치가 아니라 문제-적합성으로 할 수밖에 없다.
- **ContextAI MCP export 성숙도는 부분 미확인**: 서버 종단이 이 저장소 밖 Flava Hub라 실제 배포·가동은 보고서 B가 판정 불가라 명시.
