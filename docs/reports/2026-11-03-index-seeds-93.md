# checkout 간 벡터 seed — BB2 work-tracker #93 엔진 결과

정본: [BB2 #93](https://git.linecorp.com/minhyun-ji/bb2-work-tracker/issues/93).
엔진 기준 `b0eb72f`, 작업 브랜치 `mooh1222/brain-seed-index-93`.
엔진 구현과 합성 검증을 이 워크트리에서 수행한다. BB2 통합·release 게시와 실제 회상 수용
검증은 별도이며, 아래 실모델 실측은 사용자의 메모리 사고 추가 지시에 따라 생략했다.

## 구현

- `index rebuild --seed <DB>` 반복 인자 > config `index_seeds` 경로 배열 > 동일 Git 공용
  디렉터리의 다른 checkout 자동 탐색. 원본 checkout을 먼저 사용한다. config 상대 경로는
  config 디렉터리 기준이며 빈 배열은 자동 탐색을 끈다.
- 자기 이전 색인 → seed 순서로 exact surface 벡터를 복사한다. 새 corpus의 객체·raw와 FTS를
  다시 조립하고 대상 DB만 검증·fsync·원자 교체한다. 다른 checkout의 DB를 공유하지 않는다.
- 공통 `_previous_vectors` reader는 URI `mode=ro`로 읽고 schema·embedding identity·tokenizer·
  extractor 일치와 기존 무결성 계약을 검사한다. 잠긴 DB는 기다리지 않고 건너뛴다.
  tokenizer·extractor 현재값 일치 검사도 자기 이전 색인과 seed에 똑같이 적용한다.
- `vectors_reused`는 자기 이전 색인, `vectors_seeded`는 seed, `vectors_computed`는 실제 계산
  행 수다. `seed_paths`는 실제 기여한 seed의 절대 경로, `seed_fallbacks`는 `{path, reason}`다.
  `vector_reuse_fallback`은 자기 이전 색인에 대한 기존 필드라 seed 성공과 독립적이다.
- `RealEmbedder.embedding_identity`는 가중치 없이 실행 설정을 해석한다. 로더에 같은
  device·float32를 명시하고 계산 뒤 신원이 바뀌면 DB 교체를 거부한다. 전량 재사용이면
  가중치 로더를 호출하지 않는다. 기존 v2 identity 형식·모델 revision·schema는 보존한다.

## 검증

CLI와 stub/외부 모델 fake를 경계로 다음을 검증했다.

- (a) 객체 2개 + raw 1개 seed 전량 재사용: seeded 3 / computed 0, cold 검색 응답 동등.
- (b) 객체 하나 변경: seeded 2 / computed 1.
- (c) identity·tokenizer·extractor·schema 불일치: seed 제외 및 구체적 사유.
- (d) 손상·SQLite exclusive lock·누락 seed fallback. 다른 정상 seed가 있으면 계속 진행.
- (e) 자기 이전 색인 2개 + seed 1개, 다음 실행에서는 자기 재사용 3개 / seeded 0.
- (f) seed 및 자기 이전 색인의 전량 재사용 시 모델 가중치 로더 호출을 금지한 테스트 통과.
- CLI/config 우선순위·상대 경로·반복 seed·동일 clone 원본 우선·손상 원본 다음 checkout·
  다른 clone 자동 탐색 제외·빈 config 배열 비활성화. seed 원본 bytes 보존.

독립 검수에서 발견한 비객체 JSON sibling config의 전체 실패와 별도 clone으로 연결된
자동 DB 후보를 CLI에서 각각 RED로 재현해 수정했다. 잘못된 config는 건너뛰고,
별도 Git clone 소속으로 확인된 DB 실경로는 `seed_clone_mismatch`로 제외한다.

최종 검증 환경은 이 워크트리의 Python 3.12.11이며 `uv sync --python 3.12 --frozen`을 사용했다.
`PYTHONPATH`와 `.venv/bin/python`을 이 checkout으로 고정했다.

| 검사 | 결과 |
|---|---|
| 전체 `python -m pytest -q` | **2,426 passed, 174 subtests passed**, 573.40초 |
| 설치 runtime unittest discover | **151 tests OK**, 15.339초 |
| seed·config·embedder·기존 재사용·architecture 표적 회귀 | 86 passed (Python 3.13); 3.12 seed CLI + lint 표적 17 passed / subtest 5 |
| `git diff --check` | 통과 |

독립 검수는 두 Sol 에이전트가 읽기 전용으로 나누어 수행했다. **Standards: 미해결 0건**,
**Spec: 최초 P2 2건 수정 후 재검수 미해결 0건**이다. 코드 커밋은 `f63be72`(구현)와
`c822502`(검수 보완)이며 push·tag·release·PR은 실행하지 않았다.

Python 3.13.6 첫 전체 실행은 2,426 passed / 173 subtests passed 뒤 기존
`TestLintStore.test_manifest_local_locator_rejects_traversal_and_symlink_escape`의 `raw/loop`
subtest 1건이 실패했다(563.58초). 기준 `b0eb72f`를 `/tmp` 계열 임시 디렉터리에 추출해
같은 실패를 재현했다. 3.13의 `Path.resolve(strict=False)`가 순환 symlink를 예외 대신
미존재 경로로 반환하면서 기존 lint가 `manifest_local_file_missing`을 내는 차이다.
BB2 release의 Python 3.12에서는 해당 표적과 전체 스위트가 통과한다. 관련 없는 lint 코드는
수정하지 않았으며 이 기존 3.13 호환 문제는 별도 후속으로 남긴다.

## 실코퍼스 실측: 안전상 생략

사용자는 재시작 후 원인 조사 전 실모델 실측 금지, 다른 임베딩과 동시 실행 금지,
실행 시 최대 RSS 기록, 위험하면 생략하도록 추가 지시했다. 16:07:56 KST 프로세스 스냅샷에서
다른 세션의 Brain 실모델 경로 `search` 4개가 동시 실행 중이었다. 16:08:24 Mole 읽기 전용
상태는 RAM 36GiB, swap 사용 약 6.25GiB/7GiB를 보고했다. 따라서 bge-m3 rebuild·eval·
실코퍼스 checks를 실행하지 않았고, BB2 corpus를 수정하거나 해당 프로세스를 중단하지 않았다.

| 항목 | 이번 결과 |
|---|---|
| 실모델 seeded / computed / 시간 / 최대 RSS | 미측정 — 모델 실행을 생략했으므로 수치 없음 |
| 대조군 | #93의 과거 cold 약 516초·8,242행. 이번 측정과의 속도비를 계산할 수 없음 |
| source DB 읽기 전용 관찰 | schema 5, bge-m3, kiwipiepy@4, extractor 4, 당시 8,352행 |
| 실제 골든셋 18/18·회상 13/13, seed/cold 동등성 | 이번 세션에서 미검증. 합성 검색 동등성과 구분 |

이후 실측은 다른 `search`·`eval`·`rebuild` 임베딩 프로세스가 없는 시점에 하나만 실행하고,
BB2 corpus의 `/tmp` 복사본과 원본 색인을 읽기 전용 seed로 사용한다. `/usr/bin/time -l`로
최대 RSS와 경과 시간을 기록한다. 원본 source DB와 BB2 파일은 수정하지 않는다.

## 15:55~16:05 메모리 사고 조사 (읽기 전용)

결론: **Brain 실모델 경로 검색 14개 동시 실행은 확인했다. 이것이 메모리 압박에 기여했을
가능성은 크지만, 강제 종료의 단일 원인·당시 가중치 로드 완료 수·최대 메모리는 확인 불가다.**
해당 구간에 이 #93 세션이 실모델 rebuild를 실행했다는 증거는 없다.

확인한 근거:

1. `/Library/Logs/DiagnosticReports`와 사용자 `~/Library/Logs/DiagnosticReports`를 하위
   디렉터리까지 확인했다. 해당 날짜·시간의 JetsamEvent·panic·memory 명칭 보고는 없다.
   `ResetCounter-2026-11-03-155816.diag`는 15:58:16 +0900의 재시작, boot failure 1,
   `rst btn_rst,btn_seq_reset timeout,dblclick_timeout target_off_restart`를 기록한다.
   이는 reset 기록이며 OOM killer·kernel panic의 증명은 아니다.
2. `Orca Helper_2026-11-03-160024_*.diag`는 15:58:32~16:00:22의 **재부팅 후 disk writes**
   보고다(2,147.49MB, Action none, Time Since Boot 107s). `com.apple.dt.SKAgent_2026-11-03-160350_*.diag`
   역시 15:58:34부터의 disk writes 보고다. 둘을 재부팅 전 OOM 증거로 해석하지 않는다.
3. `~/.codex/sessions/2026/11/03/`의 rollout 22개에서 15:45~16:06 KST
   (06:45~07:06 UTC) 이벤트를 대조했다. agent-env-share 워커 세 개가 실모델 경로 검색을
   각각 15:53:58에 5개, 15:54:04에 6개, 15:54:45에 3개 시작했다. 검색 명령에는
   `--stub-embedder`가 없고 환경 prefix에도 stub 강제가 없다. 검색은 query 벡터를 만들 때
   `get_embedder()` → `RealEmbedder` → bge-m3를 사용하는 코드 경로다.
4. `rollout-2026-11-03T12-30-44-01a19f75-8dd1-7342-aeda-2644d12f4337.jsonl:1884`의
   15:55:21.795 프로세스 스냅샷에 위 검색 **14개가 실제로 동시에 존재**한다.
   다른 두 시작 근거는 `...12-30-43-01a19f75-88bc-76a1-b0c8-40c9eee6f5e7.jsonl:1655`,
   `...12-30-42-01a19f75-87d6-7fe3-aef1-b6f21e9f261d.jsonl:1706`이다.
   검색을 실행한 사실과 모든 모델이 가중치 로드를 완료한 사실은 다르다.
5. 같은 구간에서 위 워커들의 실제 index rebuild·직접 embed 실행은 확인하지 못했다.
   소스·지시서·과거 결과에 나온 문자열은 실행으로 세지 않았다. mountain-dash의 초안 갱신도
   index 실행 증거로 취급하지 않았다. 이 조사는 Codex 날짜 폴더 범위라 Copilot·비기록 셸까지
   완전 포괄했다고 주장하지 않는다.

이 세션 자신의 실행 이력(`...15-52-51-01a1a02e-9ab3-7a83-84cb-8eafff551269.jsonl`):

- 중단 전: 15:53:14 `uv sync`로 의존성을 설치했다(torch **다운로드/설치**, 모델 실행 아님).
  15:54:34 첫 pytest는 pytest 미설치로 종료했다. 이후 테스트는 `--stub-embedder`를 지정한다.
  source index metadata를 읽기 전용 SQLite로 조회했다. 실모델 rebuild·eval·직접 embed는 0회다.
- 재개 후: 합성 stub 테스트와 외부 모델 fake를 실행했다. 모델 미로딩 테스트의 초기 버전에서
  `patch.dict(sys.modules)` 복원 후 PyTorch native 모듈 재import가 segfault(exit 139)를 냈다.
  bge-m3는 가짜 모델이었고 실제 가중치는 로드하지 않았다. PyTorch 경계도 fake로 격리해
  수정하고 해당 테스트를 재실행했다. 이는 재부팅 전 사고와 시각·프로세스가 다른 사건이다.
- 다른 세션의 파일·프로세스·설정에는 쓰기·종료·청소를 하지 않았다.

운영 후속은 rebuild뿐 아니라 `search`·`eval`도 포함해 실모델 사용을 직렬화하는 것이다.
그 운영 변경·전역 임베딩 서비스·검색 동시성 정책은 이번 엔진 seed 구현에 추가하지 않는다.

## BB2 통합과 남은 일

- 후속 엔진 release가 나오면 `scripts/agents/brain-release.json`의 `version`, `status`,
  `release_url`, `artifacts` 파일명·SHA256(wheel·constraints·SHA256SUMS)을 실제 게시 값으로
  갱신한다. release tag와 commit도 확인 기록에 남긴다. 이번에는 version 상향·push·tag·
  release·PR을 실행하지 않는다.
- bb2-setup `prepare`의 brain-index: 호환 seed가 있으면 “빠른 색인”으로 분류해 실행,
  없으면 기존 예상 시간·확인을 유지한다. seed 존재만으로 computed=0을 보장하지 않으므로
  실제 후보 호환성과 결과의 seeded/computed·fallback을 안내한다. 가짜 brain 명령으로 분류를
  검증하는 BB2 테스트는 그 저장소 후속이다.
- TEAM_SETUP에는 “DB는 checkout별, 벡터는 동일 clone의 호환 seed에서 재사용, 전량 재사용이면
  가중치 미로딩”을 반영한다. `.local/brain-tools` clone 공유는 별도 결정으로 남긴다.
- 안전한 환경에서 실모델 시간·최대 RSS와 골든셋 18/18·회상 13/13 동등성을 확인해야 한다.
  이 보고의 엔진 합성 통과를 BB2 실측 수용 완료로 대신하지 않는다.
