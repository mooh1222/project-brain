# Brain 기록·회상 Interface 설계 검토

작성: 2026-11-04. 상태: 구현 전 설계안. 사용자 요청은 codebase-design 기준의 판단·설계와 to-spec 작성이다. 이 문서는 구현·배포·코퍼스 이관의 결과가 아니다.

같은 날 설계 리더 검토에 대한 합의와 사용자 확정 결정 2건을 반영했다. 공통 판단은 작은 별도 reference 파일에 두고, 백로그의 진행 상태 필드는 제거하며 채택 시 이슈·작업 링크 한 줄만 남긴다.

## 사용자 결과

사용자 목표는 “브레인 목적에 맞는 분류 및 실제 활용가능해야 됨”이다. Brain의 목적은 에이전트가 프로젝트 지식과 근거를 다시 회수하여 답변과 개발 판단에 사용하는 것이다. 기록 종류를 설명할 수 있는 것만으로는 이 목표를 달성하지 못한다.

최초 사용 가능 결과는 다음 세 요청이 저장 위치를 알려주지 않아도 동작하는 것이다.

- “이 주제 조사하던 거 이어가자”: 관련 지식 초안의 이해·근거·미결과 적재 지식을 구분해 재개한다.
- “여기 수정할 때 주의할 점 있어?”: 관련 근거와 검수된 Insight를 회수한다.
- “전에 공통화하자던 게 뭐였지?”: 저장된 개선 제안을 직접 찾아 출처와 현재 확인 한계를 제시한다.

사용자는 전 작업 자동 훑기를 원하지 않는다고 밝혔고, draft를 지식 초안이라고 정정했다. Insight도 적재 지식이라는 관계를 분명히 해야 한다. 이 정정들이 설계의 출발점이다.

현재 엔진은 draft의 생성·선택 읽기·갱신, 기존 객체 적재, Insight의 reviewed-only advisories를 이미 제공한다. 이 실행 기능이 없어서 생긴 문제가 아니라, 호출자가 알아야 할 목적별 규칙이 분산되고 일부 회상 지시가 빠진 문제다.

## Module과 Interface

설계 대상 Module은 설치된 Brain 스킬들이 제공하는 기록·회상 처리다. 새로운 Python Module을 만든다는 뜻은 아니다. 이 Module의 Interface에는 자연어 요청뿐 아니라 읽기/기록 의도, 근거 상태, 명령 순서, 조회 실패와 부재의 차이도 포함된다.

사용자에게 보이는 Interface는 다음과 같다.

- 입력: 요청의 목적, 관련 자료, 작업·주제 맥락. 사용자에게 객체 kind나 저장 폴더 선택을 요구하지 않는다.
- 결과: 근거와 상태를 구분한 답변, 또는 적절한 기록과 그 위치·다음 행동에 대한 짧은 보고.
- 불변: 조회는 무쓰기, 초안은 미검수 작업 기억, 적재 객체는 기존 검수 상태 유지, 개선 제안은 실행 확정이 아님.
- 순서: 일반 지식 조회는 관련 초안 발견 후 search→핵심 show, 개선 제안 조회는 목적에 맞는 직접 읽기, 정식화는 기존 ingest.
- 실패: 조회 실패·불완전 목록·실제 빈 결과를 구분한다. 준비가 안 된 도구를 조회 중 자동 설치하거나 색인을 재생성하지 않는다.

설치 스킬의 자연어 진입점이 외부 Seam이며, 실제 호출 조건을 노출하는 frontmatter description도 그 Interface에 포함된다. 공통 판단 reference와 기존 명령 호출은 내부 Seam이다. 최종 판단과 사용자 답변은 기존 에이전트가 맡으며 엔진의 결정론 검증과 혼동하지 않는다.

query의 description에는 “전에 ~하자던 거”, “남은 개선” 같은 개선 제안 회상 요청을 추가한다. session-ingest의 description에서는 “검증 대기로 보관”을 기본 신규 기록 경로로 유도하는 표현을 정리하고, 지식 초안·적재·개선 제안의 목적에 맞게 연결한다. 과거 검증 대기 기록의 명시적 조회는 유지한다.

## 세 대안의 비교

### A. 기존 스킬 + 공통 판단 정본

기존 query·draft·session-ingest·ingest 진입점을 유지한다. 목적별 기록·회상 판단만 담는 작은 별도 reference 파일을 두고, 여러 스킬은 필요한 상황에 이를 읽는다. 이 파일이 실제 분류·회상 판단을 소유하며 링크 목록이나 복제된 요약만 모으지 않는다.

- Depth: 사용자가 저장 분류를 배우지 않고 기록·회상·정식화를 요청할 수 있다.
- Locality: 목적별 분류 규칙과 근거 부족 처리의 변경이 한곳에 모인다.
- Leverage: 네 진입점과 설치된 여러 소비 프로젝트가 같은 판단을 재사용한다.
- 한계: 지침을 읽고 따르는 에이전트의 실제 동작을 검증해야 한다. 문서만으로 의미 판단을 결정론적으로 강제한다고 주장할 수 없다.

### B. 새 프로그래밍된 판단 Module

기록/회상 의도와 자료 메타데이터를 받아 다음 행동을 반환하는 새 Module을 둔다. 원문 의미를 분류하려면 현재 없는 의미 판단 Implementation이 필요하다. 분류 enum을 입력받으면 그 판단 부담은 호출자에게 남고 Module은 명령을 전달하는 역할만 하게 된다.

- Depth: 현재 숨길 수 있는 결정론 동작은 이미 기존 명령에 있으므로 추가 Leverage가 작다.
- Locality: 코드상 판단 위치는 모을 수 있지만 에이전트의 의미 판단과 새 Interface를 함께 유지해야 한다.
- 비용: 새 호출 규약·오류·가능한 CLI 또는 결과 형식을 사용자가 요구하지 않은 상태에서 추가한다.
- 판정: 현재 목표에는 채택하지 않는다.

### C. 각 스킬을 최소 수정

새 공통 정본을 두지 않고 각 스킬에서 필요한 판단만 고친다. 흔한 기능 질문·재개 흐름은 기존 Interface 그대로다.

- Depth: 새 진입점이나 reference를 배우지 않고 기존 기능을 활용한다.
- Locality: 개별 흐름 가까이에 안내가 있지만 분류 정책 변경은 여러 스킬에 흩어진다.
- 비용: 현재처럼 같은 지식의 대기 위치를 다르게 안내하는 회귀가 재발할 수 있다.
- 판정: 즉시 패치로는 작지만 이번 문제의 원인인 분산 판단을 그대로 남긴다.

## 선택: A, 작은 공통 reference에 판단을 모은다

새 정책 registry나 라우터를 추가하지 않는다. 기존 installer가 전달하는 작은 별도 reference 파일에 목적별 기록·회상 판단을 모은다. 객체 모델 reference는 ingest 조립·객체 필드 계약을 계속 소유하며 query가 회상 판단만을 위해 그 전체를 읽게 하지 않는다. 공통 초안 발견 reference처럼 여러 스킬이 같은 파일을 참조하는 선례를 재사용한다. 상세 객체 필드 검증, 초안 발견·갱신, 적재 최종화의 기존 소유는 유지한다.

deletion test는 다음과 같다.

- 공통 판단 reference를 지우면 목적·검수 상태·실행 행동을 나누는 복잡성이 네 호출자에 다시 생긴다. 이 파일은 실제 Locality와 Leverage를 제공한다.
- 새 프로그래밍 라우터를 지워도 기존 명령과 에이전트의 의미 판단은 그대로 남는다. 현재 요청에서 새 라우터는 충분한 Depth를 얻지 못한다.
- pending의 기본 신규 기록 분기를 줄이면 독립 소비자가 없는 선택지가 줄어든다. 유용한 조사 주제는 draft, 검수 가능한 내용은 기존 적재, 개발 개선 행동은 backlog로 처리하며 기존 자료를 버리지 않는다.

## 분류와 활용 계약

| 사용자 관점 | 의미 | 기록·조회 책임 |
|---|---|---|
| 지식 초안 | 주제별 이해·근거·가설·결정·미결을 이어서 다듬는 작업 공간 | draft가 생성·선택 읽기·SHA 기반 갱신을 소유하고 query/session-ingest는 기존 발견 절차로 연결한다. |
| 적재 지식 | 기존 Brain 객체. Insight도 여기에 속한다. | ingest가 근거 대조와 기존 검수를 거쳐 적재하고 query가 search→show로 회수한다. |
| 개선 제안 | 나중에 검토할 구체적인 개발 개선 행동 | session-ingest의 기록 흐름에서 보존하고 개선 제안 질문에서 query가 직접 읽는다. 실행 관리는 기존 작업·이슈가 소유한다. |

raw는 원문 근거층이며 위 세 분류에 더하는 합성 메모함이 아니다. 기존 객체의 candidate/reviewed는 검수 상태이고, draft와 동의어가 아니다. candidate Insight를 새로 허용하지 않는다.

Insight는 다음 작업에서 참고할 판단이 있고 근거 객체·적용 범위가 있는 종합 위험·교훈으로 제한한다. 단일 동작의 설명은 해당 기존 객체로 적재한다. “규칙이 두 진입 경로에 흩어져 수정 때 함께 확인해야 한다”는 교훈은 Insight, “그 코드를 공통화하자”는 개선 제안이다.

초안은 기능 외의 조사·도메인 주제도 허용하며 항목 수 문턱을 두지 않는다. 모든 미정리 생각에 초안을 만들지는 않는다. 충분히 확인된 내용의 직접 적재 요청에는 초안을 필수 선행 단계로 요구하지 않는다.

pending은 기본 신규 기록 경로에서 제외한다. 기존 파일과 이력은 보존하고 기존 후보를 조회할 때는 미검증으로 표시한다. 이 결정은 다른 이름의 pending 상태나 적재 보고서 필드에 대한 일괄 삭제 지시가 아니다.

## 정식화와 소유

선택한 초안 내용을 기존 적재 절차로 검수·적재한 후, 초안에는 기존 객체 참조와 남은 미결을 반영한다. 같은 현재 사실을 독립 정본 둘로 유지하지 않는다. 초안의 정리는 기존 갱신 Interface로 수행하며 자동 승격·close 상태·새 장부는 만들지 않는다.

적재가 끝났지만 초안 갱신에 충돌이 생기면 두 결과를 구분해 보고한다. 적재 성공을 취소하거나 같은 내용을 무조건 다시 적재하지 않고, 최신 초안을 읽어 기존 갱신 방식으로 보완한다. 두 효과를 새 원자 transaction으로 묶지 않는다.

개선 제안의 기록은 구현 확정이 아니다. 기록된 날짜·출처·검증 한계와 제안이라는 성격은 보존한다. 백로그 형식에서 `진행 상태: 미착수/진행 중/완료/보류` 필드를 제거한다. 채택 시 이슈·작업 링크 한 줄만 남기며 실행 진행은 그 링크 대상이 소유한다. 채택 여부를 위한 별도 상태 필드도 추가하지 않는다. 과거 기록에 남은 “미착수” 표시는 현재 코드가 여전히 미해결임을 증명하지 않는다.

엔진은 백로그 파일을 scaffold하지 않는다. 설정된 Brain 루트와 접근 가능 여부를 확인한 뒤 백로그 파일이 없으면 해당 저장 위치의 정상 빈 결과로 답하고 파일을 자동 생성하지 않는다. 루트 해석 실패·권한 오류·불완전 조회를 파일 부재로 취급하지 않는다.

## 의존과 Adapter

- 파일·Git·설치 CLI는 local-substitutable 의존이다. 기존 명령과 임시 소비 프로젝트로 관찰할 수 있다.
- 의미 분류·답변 판정은 기존 에이전트가 수행한다. 새 코드 판단 Module이나 의미 검증기를 도입하지 않는다.
- 스킬 지침에 추상 port를 추가해야 할 실제 두 Adapter가 없다. 새 Adapter 계층을 만들지 않는다.
- 기존 엔진의 SHA 갱신, 검수 상태, 검색 채널과 installer 소유권을 재사용한다.

## Test Seam과 완료 판정

최상위 Test Seam은 설치된 스킬의 자연어 Interface다. 합성 소비 프로젝트의 기록 세션과 새 회상 세션을 사용해, 저장 경로를 미리 알려주지 않은 요청에서 실제 파일과 본문을 찾아 답하는지 확인한다. 문구 존재·파일 생성·스킬 노출만 확인해서는 완료가 아니다.

관찰은 자연어 요청, 선택된 기존 스킬·명령, 실제 기록/읽기 결과, 답변의 출처·검수 상태, 조회 전후 무변경을 함께 연결한다. 합성 소비 프로젝트와 StubEmbedder·결정론 토큰화를 사용하며 실제 임베딩 모델이나 실코퍼스 변경을 요구하지 않는다. 스킬을 실행하는 에이전트 모델과 엔진 테스트의 임베딩 대체물을 구분한다. 기존 installer 회귀와 설치 runtime 검사는 유지하되 이 결과를 의미 동작의 대용으로 삼지 않는다.

회차·실행 에이전트/모델·판정자·증거 형식·통과 기준은 [스펙의 실행 프로토콜](../specs/2026-11-04-brain-knowledge-workflow.md#실행-프로토콜)을 정본으로 따른다. 새 평가 파이프라인은 만들지 않는다. 기존 `tests/test_agent_skill_contract.py`의 `test_installed_ingest_skills_preserve_user_work_and_pending_boundaries`도 갱신 대상으로 포함한다. pending 파일명 존재 요구만으로 신규 기록 경로를 강제하지 않고, 기존 자료 보존과 신규 기록 유도 제외를 함께 검증한다.

설치 과정에서 사용자 수정 때문에 스킬이 skipped이면 보존하고 미적용 범위를 보고한다. 설치 결과가 존재한다는 이유로 새 지침이 적용됐다고 보고하지 않는다. 기존 draft·검색·ingest의 유효한 회귀를 삭제하거나 새 정책의 구현 문구를 그대로 복제한 테스트를 늘리지 않는다.

## 이번 산출물과 적용 범위

이번 산출물은 이 설계 검토와 별도 스펙이다. 후속 구현의 최소 범위는 엔진이 관리하는 스킬 지침·작은 별도 공통 reference·저장 규약의 정합성과 표적 검증이다. 소비 프로젝트의 규약 갱신은 그 소유 위치에서 수행하며, 엔진 레포에 실제 코퍼스나 사내 근거를 넣지 않는다.

후속 구현은 기존 dirty checkout의 WIP를 보존하고, 당시 최신 origin/main을 기준으로 새 워크트리에서 진행한다. 이번 문서도 구현 범위에 포함하되 문서와 구현의 커밋·게시 실행은 해당 요청 범위에서 판단한다. 현재 checkout을 pull·merge하거나 이 문서 수정만으로 구현을 시작하지 않는다.

### 소비 프로젝트 적용 시 확인

- BB2의 query·draft 스킬과 draft 발견 reference는 의도적 수정본으로 검토되었다. 실제 적용 시 installer 결과를 확인하고 `TEAM_SETUP.md`의 release 갱신 절차에 따라 skipped 파일을 수동 병합한다. 미수정으로 검토된 파일도 적용 시점의 해시·manifest를 기준으로 판정한다.
- BB2 소유 `brain/README.md`의 기록·회상 규칙, `brain/pending/insights.md`의 신규 기록 중단·기존 보존 머리말, 백로그 형식을 맞춘다. 기존 항목·출처·이력은 보존한다.
- release로 전달하는 경우 정식 artifact와 release 고정 정보·installer manifest를 일치시키고 `bb2_setup.py check --all-refs` 및 Brain 조회 스모크를 확인한다. 버전 번호는 당시 release 상태에 따라 정하며, 스킬·비색인 규약만 바뀌는 범위에서는 색인 rebuild가 필요하지 않다.
- 실제 BB2 조회 확인이 요청된 경우 새 세션에서 “빅버블 공통화하자던 거”, 관련 수정 주의사항, 조사 초안 재개를 읽기 전용으로 확인한다. 이 확인을 합성 소비 프로젝트의 실행 증거와 구분한다.
- 임베딩 서비스 안내의 엔진 upstream과 mountain-dash 등 다른 워크트리 동기화는 별도 적용 범위다. 기존 안내는 병합 중 보존하되, 이번 분류·회상 개선의 필수 완료 조건으로 묶지 않는다.

새 kind·schema·CLI 의미·검색 채널·색인·자동 스캔·이슈 동기화·삭제/승격 상태머신은 필요하지 않다. 실제 소비 코퍼스 이동·삭제, 전역 설치 변경, 실모델 rebuild, 원격 게시를 이번 문서 작성에 포함하지 않는다.

## 범위 검수

최초 스펙 작성 후 새 읽기 전용 문맥에서 최신 사용자 원문과 두 문서 및 당시 코드를 대조했다. 당시 판정은 계약 위반·계약 공백 없음이었다. 이번 보완은 후속 설계 리더 검토와 사용자가 수용한 결정의 반영이며 새로운 독립 검수의 실행 결과는 아니다. 현재 이 문서의 존재는 구현 검증의 증거가 아니다.

- 검토 대상: 이 설계와 같은 날짜의 Brain 기록·회상 스펙.
- 완료산출물: 지식 초안·적재 지식·개선 제안을 목적에 맞게 기록하고 질문으로 회수하는 기존 스킬 흐름. 이번 작업은 이를 설계·명세하는 단계다.
- 첫 사용 가능 결과: 저장 경로·스킬명·객체 ID·이전 대화 없이 새 세션이 관련 초안을 재개하고 Insight와 개선 제안을 실제 본문·출처로 답한다.
- 결과 반례: 분류표와 설치 파일만 갖추고 질문으로 기록을 못 찾는 결과는 W-T1~W-T3을 통과할 수 없다. 문구·파일 존재만으로 완료할 수 없고 W-T1~W-T7의 실행 증거가 필요하다.
- 추가 의무 연결·소유 확인: 작은 별도 공통 reference는 분산된 현재 지침을 모으고, description과 개선 제안 직접 읽기는 현재 query의 회상 누락을 닫는다. 백로그의 진행 상태 제거는 실행 소유를 기존 작업·이슈에 유지한다. 실행 프로토콜은 기존 W-T1~W-T7의 관찰 조건을 고정하며 새 평가 제품을 추가하지 않는다. 상태·근거 구분과 기존 자료·설치 소유권 보존은 안전하게 기록을 활용하는 최소 조건이다. 기존 ADR의 후속 기능을 새 의무로 승계하지 않는다.
- 제외 목록: 새 kind·schema·CLI·검색 채널·전수 발견·자동 훑기/승격/삭제·이슈 동기화·새 장부/평가 체계·실코퍼스 이관·전역 설치·게시. 현재 목표에 필수라는 근거가 없는 범위 제안이며 비차단이다.
- 허용 불완전성: metadata 밖 개별 지식의 전수 발견을 보장하지 않는다. 부분 조회와 접근 실패는 한계를 표시하며 가능한 조회를 계속한다. 적재 후 초안 갱신 충돌은 결과를 나눠 보고하고 기존 SHA 갱신으로 보완한다.
- 계약 공백: 현재 설계·스펙 요청 범위에서 확인되지 않았다. 문서 단계에 실행 증거가 없다는 사실을 구현 성공으로 확대하지 않는다.

이 제외 목록과 허용 불완전성은 후속 설계·검수의 기준 계약이며, 제외 항목의 재포함에는 현재 사용자 결과와의 연결 근거가 필요하다.

문서 검사는 to-spec의 필수 7개 절, 24개 사용자 이야기, Implementation Decisions의 특정 파일 경로·코드 예시 없음, 상대 링크 대상의 존재, 공백·마지막 개행을 확인한다. 실행 코드와 설치 템플릿은 변경하지 않았으므로 이 문서 작성 작업에서 엔진·소비 프로젝트 실행 회귀를 수행했다고 주장하지 않는다.
