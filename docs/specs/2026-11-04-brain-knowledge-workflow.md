# Brain 기록·회상의 분류와 사용 경로 정리

작성: 2026-11-04. 상태: 구현 전 스펙. 사용자 요청에 따른 codebase-design 검토 결과를 반영한다. 이번 산출물은 설계·스펙 작성이며 구현·배포·코퍼스 이관의 결과가 아니다.

같은 날 설계 리더 검토에 대한 합의와 사용자 확정 결정 2건을 반영했다. 공통 판단은 작은 별도 reference 파일로 분리하고, 백로그의 진행 상태 필드는 제거하며 채택 시 이슈·작업 링크 한 줄만 남긴다.

## Problem Statement

Brain은 에이전트가 프로젝트 지식과 근거를 회수하여 답변과 개발 판단에 사용하는 엔진이다. 현재 안내는 지식 초안, 적재 객체, Insight, 검증 대기 인사이트(기존 기록), 개발 개선 백로그를 서로 다른 기준으로 설명한다. 사용자는 무엇을 어느 곳에 남겨야 하는지, Insight도 적재 지식인지, 남긴 개선 제안을 나중에 어떻게 다시 꺼내는지 혼동한다.

지식 초안은 이해·근거·가설·미결을 주제별로 이어가는 작업 공간인데 미검증 후보를 보관하는 임시함처럼 축소될 수 있다. 미검증 교차 분석은 검증 대기 영역으로, 근거 객체가 준비되지 않은 Insight는 백로그로 보내는 상충 안내도 있다. 개선 제안의 보존 규약은 있으나 조회 스킬에 이를 자연어 질문으로 직접 읽는 분기가 명확하지 않다.

폴더와 이름을 정리하는 것만으로 해결되지 않는다. 사용자가 기록 위치를 기억하거나 과거 대화를 전달하지 않아도, 새 에이전트 세션이 기록을 발견하고 근거·검수 상태를 구분하여 활용할 수 있어야 한다.

## Solution

사용자 관점의 운영 분류를 지식 초안·적재 지식·개선 제안으로 정리한다. Insight는 적재 지식의 기존 종류로 유지한다. 원문은 이 지식을 뒷받침하는 근거층으로 보존한다.

사용자는 저장 종류나 객체 kind를 직접 고르지 않는다. 기존 스킬이 요청의 목적과 내용을 해석하고, 기존 명령을 사용하여 기록하거나 회수한다. 목적별 기록·회상 판단을 작은 별도 reference 파일에 모으고 각 스킬이 같은 판단을 사용하게 한다. 새 명령이나 코드 라우터를 추가하지 않는다.

일반 기능 질문·개발 재개는 관련 초안 발견과 적재 지식 회수를 사용한다. 개선 제안 질문은 보존된 백로그를 직접 읽는다. 조회는 읽기 전용이며, 초안·후보 객체·원문 발췌·검수된 객체의 차이를 답변에서 유지한다. 검증 대기 인사이트(기존 기록)는 신규 기록의 기본 선택지에서 제외하되 기존 기록을 보존한다.

## User Stories

1. 사용자로서, 저장 폴더나 객체 종류를 외우지 않고 기록을 요청하여 내용에 맞는 형태로 보존하고 싶다.
2. 개발자로서, 조사 중 이해·근거·가설·미결을 지식 초안에서 이어가서 다음 작업 구간에 다시 설명하지 않고 싶다.
3. 개발자로서, 여러 기능에 걸친 조사도 하나의 지식 주제로 기록하여 공통 위험을 놓치지 않고 싶다.
4. 개발자로서, 내용이 한 항목이어도 유용한 주제와 출처가 있으면 초안으로 남겨 불필요한 크기 문턱 없이 재개하고 싶다.
5. 사용자로서, 충분히 확인된 내용은 기존 적재 절차로 바로 넘겨 초안을 필수 대기 단계로 거치지 않고 싶다.
6. 사용자로서, Insight를 다른 기능 지식과 함께 적재되는 객체로 이해하여 별도 메모 저장소처럼 관리하지 않고 싶다.
7. 개발자로서, 관련 기능을 수정할 때 검수된 위험·교훈을 주의사항으로 회수하여 같은 실수를 피하고 싶다.
8. 적재자로서, 단일 기능 설명과 여러 근거에서 종합한 교훈을 기존 객체 종류로 구분하여 중복되거나 추상적인 Insight를 늘리지 않고 싶다.
9. 사용자로서, 나중에 검토할 개선 행동을 제안으로 남겨 구현이 확정된 작업과 혼동하지 않고 싶다.
10. 사용자로서, “전에 공통화하자던 것” 같은 질문으로 저장된 개선 제안을 찾아 당시 출처와 확인 한계를 알고 싶다.
11. 적재자로서, 근거가 부족한 지식을 개발 개선 백로그로 보내지 않고 해당 초안의 미결로 남겨 기록의 목적을 유지하고 싶다.
12. 사용자로서, 한 요청에 이해와 개선 행동이 함께 있으면 필요한 지식과 행동을 나누어 보존하고 싶다.
13. 조회자로서, 관련 초안을 찾고 필요한 본문과 출처를 읽어서 요약이나 제목만으로 사실을 단정하지 않고 싶다.
14. 조회자로서, 초안의 가설·미검수 후보와 검수된 지식을 구분해서 불확실한 내용을 현재 사실처럼 답하지 않고 싶다.
15. 조회자로서, 접근 실패·불완전 목록·색인 오류와 정상적인 빈 결과를 구분하여 “기록 없음”이라는 잘못된 결론을 피하고 싶다.
16. 사용자로서, 조회 요청으로 기록·검수 상태·색인·Git 상태가 바뀌지 않아 안심하고 질문하고 싶다.
17. 사용자로서, 오래된 개선 제안이 현재도 미해결인지 확인되지 않았음을 알아 과거 기록을 현재 작업으로 오인하지 않고 싶다.
18. 개발자로서, 채택한 작업의 실행은 기존 작업·이슈에서 관리하여 백로그와 진행표를 중복 운영하지 않고 싶다.
19. 사용자로서, 검증 대기 인사이트(기존 기록) 및 이전 초안 형식을 보존하여 분류 정리를 이유로 이력을 잃지 않고 싶다.
20. 적재자로서, 초안을 정식화한 뒤 적재 객체 참조와 남은 미결을 반영하여 같은 사실을 독립된 두 정본으로 관리하지 않고 싶다.
21. 유지보수자로서, 목적별 분류를 한 정본에서 고쳐 여러 설치 스킬의 안내가 어긋나지 않게 하고 싶다.
22. 소비 프로젝트 관리자로서, 사용자 수정 파일을 보존하고 적용되지 않은 지침을 알려주어 설치 성공을 동작 적용으로 오인하지 않고 싶다.
23. 사용자로서, 다른 Brain 루트 설정에서도 같은 요청을 사용하여 특정 개인 경로나 브랜치에 의존하지 않고 싶다.
24. 유지보수자로서, 설치된 스킬의 자연어 기록·회상을 새 세션에서 확인하여 문구 정리만으로 실제 활용을 완료 처리하지 않고 싶다.

## Implementation Decisions

### 1. Module·Interface·Seam

- Module은 기존 설치 스킬들이 제공하는 기록·회상 처리다. 새로운 Python Module을 요구하지 않는다.
- 외부 Interface는 요청의 목적·자료·작업 맥락을 받아 근거 있는 답변 또는 기록 결과를 제공하는 기존 스킬 진입점이다. 저장 종류를 사용자가 미리 분류하는 입력으로 추가하지 않는다.
- 외부 Seam은 설치된 스킬의 자연어 진입점이다. 기존 명령과 공통 판단 reference는 내부 Seam이다.
- 목적별 기록·회상 판단의 단일 정본을 작은 별도 reference 파일에 둔다. 각 스킬은 필요한 상황에 그 파일을 읽고, 동일한 분류표를 별도로 유지하지 않는다. query가 회상 판단만을 위해 객체 필드 계약 전체를 읽게 하지 않는다.
- 공통 reference는 목적별 배치·조회 분기·검수 상태 표시를 소유한다. 초안 발견, 객체별 상세 계약, 적재 검수·최종화는 기존 소유 Module에 남긴다. 기존 공통 초안 발견 reference의 설치·교차 참조 방식을 재사용하며 registry는 추가하지 않는다.
- 자연어 진입 Interface의 호출 조건인 frontmatter description도 갱신한다. session-ingest의 “검증 대기로 보관”을 기본 신규 기록으로 유도하는 표현을 정리하고, query에는 “전에 ~하자던 거”, “남은 개선” 같은 개선 제안 회상 트리거를 추가한다. 과거 검증 대기 자료의 명시적 조회는 유지한다.
- 로컬 파일·Git·설치 명령은 local-substitutable 의존이며 기존 임시 소비 프로젝트 검증을 사용한다. 새 port나 Adapter 계층을 도입하지 않는다.

### 2. 분류와 검수 상태

| 분류 | 내용 | 주요 회상 방식 |
|---|---|---|
| 지식 초안 | 주제별 이해·출처·가설·결정·미결을 이어가는 작업 지식 | 기존 초안 목록·선택 읽기 |
| 적재 지식 | 기존 객체 종류로 구조화된 프로젝트 지식. Insight 포함 | 기존 search와 show, Insight는 advisories |
| 개선 제안 | 나중에 검토할 구체적인 개발 개선 행동 | 목적에 맞는 직접 읽기 |

- 원문은 근거층이다. 에이전트가 해석한 요약·가설·개선 제안을 원문으로 저장하거나 원문 검색에 섞지 않는다.
- 객체 종류와 검수 상태는 다른 축이다. 기존 candidate/reviewed 등 지원 상태를 유지하며, 후보 객체를 지식 초안과 같은 개념으로 취급하지 않는다.
- Insight는 근거 객체와 적용 범위를 가진 종합 위험·교훈이다. 현재의 reviewed-only 적재·회수 계약과 source 개수 조건을 유지한다.
- 단일 동작 설명은 해당 기존 객체 종류로 적재한다. “여러 진입 경로의 동일 규칙을 수정할 때 함께 확인해야 한다”는 교훈과 “이를 공통화하자”는 개선 행동을 구분한다.
- “근거 객체를 먼저 적재해야 함”은 초안의 한계·열린 질문 또는 기존 적재의 보완 사항이다. 개발 개선 행동으로 간주해 백로그에 보내지 않는다.

### 3. 기록과 정식화

- 기존 기록 권한 안에서 요청의 목적과 내용을 판단한다. 필요한 자료나 갱신 대상이 실제로 모호할 때만 기존 확인 절차를 사용하고, 사용자에게 내부 kind 선택을 요구하지 않는다.
- 초안의 주제는 기능뿐 아니라 도메인·조사 주제일 수 있다. 유용한 주제·출처·재개 가치가 있으면 단건도 허용한다. 모든 미정리 생각이나 모든 작은 작업에 새 초안을 강제하지 않는다.
- 확인된 이해와 가설·질문·한계를 초안에서 구분한다. 형식·quote·hash 확인을 의미 검증으로 간주하지 않는다.
- 기존 초안의 생성·선택 읽기·SHA 기반 갱신·재료 준비 Interface를 그대로 사용한다. 기존 형식을 강제 변환하지 않는다.
- 충분히 확인된 내용의 직접 적재 요청은 기존 ingest로 처리한다. 초안의 생성이나 검증 대기 등록을 필수 선행 단계로 두지 않는다.
- 정식화는 선택한 내용과 실제 원문을 대조하고 기존 검수·coverage·최종화 절차를 따른다. 초안이나 준비 packet 자체를 원문 근거 또는 적재 승인으로 사용하지 않는다.
- 정식화 뒤 기존 초안 갱신으로 적재 객체 참조와 남은 미결을 반영한다. 자동 전체 승격·close·삭제 또는 새 적재 장부를 만들지 않는다.
- 적재가 성공했지만 초안 후속 갱신이 충돌하면 성공한 적재와 남은 초안 정리를 구분해 보고한다. 최신 초안을 읽고 기존 갱신 Interface로 보완하며 동일 내용을 무조건 재적재하거나 새 복합 transaction을 만들지 않는다.
- 개선 제안은 문제·기대 효과·출처·검증 한계를 기존 기록 방식으로 보존하고 제안이라는 성격을 명시한다. 백로그 형식에서 “진행 상태: 미착수/진행 중/완료/보류” 필드를 제거한다. 실제 실행으로 채택되면 이슈·작업 링크 한 줄만 남기고, 진행은 그 링크 대상이 소유한다. 채택 여부를 위한 별도 상태 필드도 추가하지 않는다.

### 4. 조회와 답변 판정

- 일반 기능 질문·개발 착수·재개는 기존 초안 발견과 search→핵심 show를 사용한다. 같은 작업 범위의 분해 질의마다 전체 초안 목록을 반복해서 읽지 않는다.
- 초안은 관련 metadata로 좁혀 필요한 본문과 출처를 읽고 미검수 작업 기억으로 표시한다. 초안에만 있는 내용과 적재 객체로 회수된 내용을 구분한다.
- 관련 reviewed Insight는 advisories에서 읽어 적용 범위와 근거를 확인하고 주의사항으로 곁들인다. 일반 사실 답변을 대체하지 않는다.
- 개선 제안·백로그 회상 요청은 기존 query 스킬의 호출 조건과 직접 읽기 분기로 명시한다. 사용자가 정확한 스킬명·저장 위치·“백로그”라는 단어를 말해야만 동작하게 하지 않는다.
- 개선 제안 질문에서 관련 파일의 실제 본문을 읽고 출처·확정 여부·확인 한계를 제시한다. 기록 존재나 과거 미착수 표시를 현재 미해결의 증거로 단정하지 않는다.
- 개선 제안만 묻는 요청에 일반 지식 검색과 전체 초안 훑기를 필수 선행으로 추가하지 않는다. 혼합 요청은 필요한 경로만 조합해 각각의 출처를 구분한다.
- 모든 경로는 프로젝트 설정이 해석한 Brain 루트를 사용한다. 특정 개인 경로·고정 브랜치·고정 설치 위치를 전제하지 않는다.
- 엔진은 백로그 파일을 scaffold하지 않는다. 설정된 Brain 루트와 접근 가능 여부를 확인한 뒤 백로그 파일이 없으면 해당 저장 위치의 정상 빈 결과로 처리하고 조회 중 파일을 생성하지 않는다. 루트 해석 실패·권한 오류·불완전 조회는 이 부재 판정과 구분한다.
- 목록 불완전·접근 오류·도구 미준비·색인 오류는 정상적인 빈 결과와 구분한다. 가능한 조회를 계속하되 실패한 범위까지 확인했다고 말하지 않는다.
- 초안과 검수된 객체가 충돌하면 주장·출처·갱신 맥락을 함께 보고한다. 최신 시각만으로 우선순위를 결정하지 않는다.
- 조회만으로 파일·객체·검수 상태·색인·stale cache·Git 상태를 변경하지 않는다. 조회 중 자동 설치나 rebuild를 추가하지 않는다.

### 5. 검증 대기 인사이트(기존 기록)의 호환

- 별도 검증 대기 인사이트(기존 기록)는 기본 신규 기록 경로에서 제외한다. 유용한 주제의 미검증 관찰은 해당 초안의 이해·가설·질문과 출처·한계로 관리한다.
- 검증 대기 인사이트(기존 기록)의 파일·항목·이력은 보존한다. 사용자가 과거 기록을 조회하면 기존 내용임과 미검증 상태를 명시하며 새 지식으로 자동 적재하지 않는다.
- 아직 지식 주제로 정리되지 않은 모든 재료에 새 합성 기록을 강제하지 않는다. 원문 출처 보존과 새로운 지식 기록 생성을 구분한다.
- 이번 변경은 검증 대기 인사이트(기존 기록)의 목적별 라우팅에 한정한다. 다른 기능의 pending 상태나 기존 적재 보고서의 보류 필드를 일괄 폐기하지 않는다.

### 6. 설치와 문서의 소유

- 엔진이 관리하는 스킬 템플릿과 공통 reference를 정본으로 수정하고 기존 installer로 소비 프로젝트에 전달한다. 설치 사본만 고쳐 엔진 정본과 갈라지게 하지 않는다.
- 소비 프로젝트의 저장 규약은 해당 프로젝트 소유 위치에서 맞춘다. 프로젝트별 경로·도구 overlay를 범용 템플릿에 하드코딩하지 않는다.
- 사용자 수정으로 갱신이 skipped된 파일과 비관리 overlay는 보존한다. 새 분류 지침이 적용되지 않은 범위를 보고하며 설치 실행 자체를 의미 동작의 성공으로 표시하지 않는다.
- 이번 설계는 기존 지원 Interface를 재사용한다. 새 객체 종류·스키마·검색 채널·색인·공개 명령 의미의 변경을 요구하지 않는다.

## Testing Decisions

### 최상위 Seam과 테스트 방식

주 테스트 Seam은 합성 소비 프로젝트에 설치된 스킬의 자연어 진입 Interface다. 기존 기록 세션과 별도의 새 회상 세션을 사용하고, 저장 경로·스킬명·객체 ID를 미리 알려주지 않은 요청에서 기록을 실제로 찾는지 관찰한다. 원래 대화 전체를 회상 세션에 넘기지 않는다.

테스트는 입력 요청, 선택된 기존 스킬·명령, 실제 기록·본문 읽기, 답변의 근거와 검수 표시, 조회 전후 상태를 연결한다. 내부 문구가 존재하거나 파일이 생성됐다는 검사만으로 완료하지 않는다. 새 세션의 모델 응답을 새 엔진 분류기의 정답 보증으로 해석하지 않는다.

| ID | 관찰 사례 | 성공 조건 |
|---|---|---|
| W-T1 | 주제의 이해·가설·미결을 기록한 뒤 새 세션에서 재개 | 적절한 초안을 찾아 필요한 본문·출처·미결로 재개한다. 단건 및 기능 외 조사 주제도 허용하고, 초안을 검수된 객체로 단정하지 않는다. |
| W-T2 | 충분히 확인된 교훈의 직접 적재와 관련 위험 질문 | 불필요한 초안을 선행하지 않고 기존 ingest를 사용한다. Insight가 적재 지식으로 저장되고 관련 advisories에서 근거·적용 범위와 함께 회수된다. |
| W-T3 | 이해와 “나중에 공통화하자”가 함께 있는 기록 요청, 이후 개선 제안 회상 | 지식과 행동의 목적을 구분해 보존한다. 정확한 분류명 없이 묻는 새 세션이 개선 제안 본문을 직접 찾아 제안과 확정·현재 확인 한계를 구분한다. 진행 상태 필드를 만들지 않고, 채택된 항목에는 이슈·작업 링크 한 줄만 남긴다. |
| W-T4 | 미확인 가설·근거 부족·오래된 기록·부분 목록·접근 또는 색인 실패 | 근거 부족을 개발 백로그나 검수된 사실로 바꾸지 않는다. 부재와 조회 실패를 구분하며 가능한 회수 결과와 불확실성을 함께 제시한다. |
| W-T5 | 설정된 Brain 루트가 다른 소비 프로젝트, 기존 형식과 검증 대기 인사이트(기존 기록), 백로그 파일 부재 | 하드코딩 없이 필요한 기록을 읽고 기존 파일·형식·이력을 보존한다. 정상 기록이 신규 검증 대기 영역으로 우회하지 않는다. 접근 가능한 루트의 백로그 파일 부재는 정상 빈 결과로 답하고 파일을 생성하지 않는다. |
| W-T6 | 조회 및 정식화 뒤 초안 갱신 충돌 | 조회는 무변경이다. 적재 성공과 초안 정리 실패를 구분하고 기존 SHA 갱신으로 보완하며 무조건 재적재하지 않는다. |
| W-T7 | 깨끗한 설치 두 번과 사용자 수정 파일·overlay가 있는 설치 | 공통 판단과 각 진입점의 참조가 설치된다. 두 번째 깨끗한 설치의 변경 배열은 모두 빈 배열이고 사용자 수정은 보존·보고된다. skipped를 적용 성공으로 보고하지 않는다. |

합성 자료는 기능 설명·서로 다른 진입 경로의 위험·구체적인 개선 행동·충분하지 않은 근거를 포함한다. 사내 코드·실코퍼스 본문·개인 머신 경로를 엔진 fixture로 복사하지 않는다. 초안 기록·기존 객체 및 검색 채널·installer의 기존 회귀를 재사용하고 문구별 동일 구현 테스트를 추가하지 않는다.

### 실행 프로토콜

- 실행 에이전트는 Codex CLI의 `gpt-6.1-sol`, reasoning effort `high`로 고정한다. 이 모델은 스킬을 사용하는 에이전트이며, 검색·엔진 검증에는 StubEmbedder와 결정론 토큰화를 유지한다. 기록·회상·판정 전 과정에서 memory·hook을 비활성화한다
  (`features.memories=false`, `memories.use_memories=false`, `memories.generate_memories=false`, `features.hooks=false`).
  실제 세션 로그에서 memory 주입·개인 memory 파일 읽기·hook 실행이 없는지도 확인한다. 실행 시작 시 실제 모델·effort·CLI 버전, 엔진 commit과 변경 diff, 설치 스킬 해시를 증거에 남긴다. 모델을 사용할 수 없으면 대체 모델로 조용히 바꾸지 않고 미실행으로 보고한다. Astra 모델은 사용하지 않는다.
- W-T1~W-T6은 각 2회 실행하며 표에 포함된 하위 사례를 회차마다 모두 확인한다. 회차마다 초기 상태가 같은 별도 합성 소비 프로젝트를 사용하고, 기록 세션과 회상 세션을 분리한다. 회상 세션에는 작업 디렉터리·통상 프로젝트 지침·설치된 스킬과 자연어 요청만 제공하고, 원래 대화·저장 경로·스킬 강제 호출·객체 ID·기대 답변은 넘기지 않는다. 충돌·조회 실패 조건은 검증 담당자가 합성 환경에 준비한다.
- W-T7은 결정론 설치 회귀 1세트를 실행한다. 깨끗한 대상에 두 번 설치하는 사례와 사용자 수정 파일·overlay가 있는 사례를 모두 포함한다. 자연어 description의 실제 발견·회상 효과는 W-T1~W-T3의 새 세션에서 확인한다.
- 판정자는 실행 세션과 분리된 검수 세션의 Codex `gpt-6.1-sol`, reasoning effort `high`다. 판정자는 요청·관찰 로그·조회 전후 파일 상태와 각 성공 조건을 대조한다. 실행자의 자기 보고만으로 통과시키지 않으며, 명령 성공·파일 존재와 본문 회수·근거 있는 답변을 구분한다.
- 증거는 `.scratch/brain-knowledge-workflow-validation/<run-id>/` 아래에 보관한다. 기존 세션 JSONL 로그, 회차별 Markdown 관찰 기록, 조회 전후 파일 해시·Git 상태를 저장하고 `summary.md`에서 사례·회차·판정·증거 링크를 연결한다. 관찰 기록은 입력 요청, 실제 선택한 스킬·명령과 결과, 읽은 본문·출처, 답변의 상태 표시, 예상 밖 쓰기 여부를 포함한다. 새 결과 schema·registry·평가 파이프라인은 만들지 않는다.
- 통과는 W-T1~W-T6 각각 2회 중 2회에서 모든 하위 성공 조건을 만족하고, W-T7의 모든 설치 조건이 통과한 경우다. 환경·모델·도구 문제로 실행하지 못한 사례는 통과에 포함하지 않는다. 실패 기록은 남기며, 수정 후에는 영향을 받은 사례를 같은 조건으로 2회 다시 확인한다. 이 결과는 고정한 환경과 요청의 재현 증거이며 모든 모델·표현에 대한 성공률 보장은 아니다.

### 기존 회귀와 완료 범위

기존 `tests/test_agent_skill_contract.py`의 `test_installed_ingest_skills_preserve_user_work_and_pending_boundaries`를 갱신 대상으로 명시한다. 현재 `pending/insights.md` 문구를 요구하는 assertion을 새 분류 계약과 맞추되, 검증 대기 인사이트(기존 기록) 및 사용자 작업의 보존 검증은 유지한다. 파일명 언급을 모두 금지하는 검사로 바꾸지 않으며 신규 기록 유도 제외와 과거 기록 조회 허용을 함께 확인한다.

엔진 자동 테스트는 기존 StubEmbedder와 결정론 토큰화 방식으로 수행한다. 템플릿 설치 변경에는 기존 installer 회귀·설치 runtime 검사·두 번째 설치의 무변경 확인을 적용한다. 실제 실코퍼스 확인은 변경 지도와 소비 프로젝트의 별도 승인 범위에 따르며, 새 세션 의미 동작 검증을 installer 검사나 스킬 노출 검사로 대체하지 않는다.

완료를 판정할 때 W-T1~W-T7의 실제 실행 증거와 정리된 안내가 함께 있어야 한다. 분류표만 정리한 결과는 완료가 아니다. 이 스펙 작성 단계에서는 이 실행 검증을 완료했다고 주장하지 않는다.

## Out of Scope

- 새 객체 kind·검수 상태 enum·후보 Insight 지원·분류 schema·공개 CLI 또는 결과 형식.
- 새 코드 라우터·의미 판단 엔진·분류 registry·Adapter 프레임워크.
- 초안·백로그의 일반 검색 색인화, 전수 발견 보장, 새 검색 채널.
- 세션 시작 또는 매 작업 전체 기록 훑기, 자동 기록·승격·삭제·close 상태머신.
- 이슈 생성·동기화·진행표 복제와 별도 backlog 관리 제품.
- 원문과 합성 지식의 혼합, 모든 미정리 생각을 보관하는 inbox.
- 검증 대기 인사이트(기존 기록)의 일괄 이동·삭제, 기존 초안 강제 변환, 과거 기록의 현재 상태 일괄 재검증.
- 새 eval 파이프라인, 실모델을 이용한 엔진 단위 테스트, 목적과 관계없는 전체 코퍼스 재적재·rebuild.
- 임베딩 서비스 안내의 엔진 upstream과 mountain-dash 등 다른 워크트리 동기화. 기존 안내는 적용 시 보존하되 별도 적용 범위로 다루며 이 개선의 필수 완료 조건으로 묶지 않는다.
- 이번 문서 작성에 따른 실제 소비 환경 변경·전역 설치 변경·commit·push·이슈/릴리스 게시.

## Further Notes

기존 지식 초안 결정은 주제별 지속 작업 공간, 비색인 발견, 선택 읽기, 기존 적재 연결을 소유한다. 이 스펙은 그 정의를 유지하면서 별도 검증 대기 인사이트(기존 기록)의 기본 신규 기록 지시와 개선 제안 회상 누락을 정리한다. ADR 0006의 주제 범위·초안 발견 선행·backlog·pending 라우팅 보류와 달라지는 결정 및
재검토 이유는 [ADR 0010](../adr/0010-align-knowledge-recording-and-recall.md)에 남긴다.
목적별 스킬 안내를 결정한 것이며 자동 상태머신 구현 요구로 확대하지 않는다.

설계 비교에서는 기존 스킬과 공통 판단 정본을 사용하는 안을 선택했다. 새 프로그래밍 라우터는 결정론 동작이 기존 명령에 있고 의미 판단이 여전히 에이전트에 남아 추가 Depth가 작다. 각 스킬을 따로 수정하는 안은 전역 분류의 Locality가 낮아 현재 드리프트를 반복할 위험이 있다.

### 후속 구현 기준점

기존 dirty checkout의 WIP를 보존하고, 구현을 시작하는 시점의 최신 origin/main을 기준으로 새 워크트리에서 진행한다. 두 문서도 그 구현 범위에 포함하되 이번 수정은 문서 작성으로 끝낸다. 현재 checkout의 pull·merge나 커밋·게시를 이 절의 실행으로 간주하지 않는다.

### 소비 프로젝트 적용

아래는 소비 환경 적용이 요청됐을 때의 확인 사항이다. 현재 문서 수정으로 설치·게시·실코퍼스 변경을 실행하지 않는다.

- BB2의 `bb2-brain-query/SKILL.md`, `bb2-brain-draft/SKILL.md`, `bb2-brain-draft/references/discovery.md`는 의도적 수정본으로 검토되었다. 적용 시점의 installer report와 manifest를 확인하고, skipped 항목은 `TEAM_SETUP.md`의 release 갱신 절차에 따라 수동 병합한다. 나머지 파일도 당시 상태를 확인하며 기존 안내를 보존한다.
- BB2 소유 `brain/README.md`의 pending 신규 기록 제외·백로그 회상 규칙, `brain/pending/insights.md`의 신규 기록 중단·기존 보존 머리말, 백로그의 진행 상태 제거·채택 링크 형식을 맞춘다. 기존 항목·출처·이력은 보존한다.
- release로 전달할 때 정식 artifact를 사용하고 `brain-release.json`과 `.project-brain-manifest.json`을 해당 버전·설치 내용에 맞춘다. `bb2_setup.py check --all-refs`와 Brain 조회 스모크를 확인한다. release 번호는 당시 상태에 따라 정하며 스킬·비색인 규약만 변경되는 경우 색인 rebuild는 하지 않는다.
- BB2 실코퍼스 확인이 요청된 경우 새 세션에서 “빅버블 공통화하자던 거”, “여기 수정할 때 주의할 점”, “조사하던 초안 이어가자”를 읽기 전용으로 확인한다. 합성 소비 프로젝트 결과와 실제 BB2 회수 결과를 구분해 보고한다.
- 임베딩 서비스 안내 upstream과 다른 워크트리 동기화는 별도 범위로 유지한다. 병합 시 기존 안내의 유실을 막는 일과 그 안내를 엔진 정본으로 옮기는 일을 구분한다.

이 스펙의 승인은 구현·설치·실제 소비 데이터 변경·원격 게시의 실행 증거가 아니다. 후속 실행에서는 해당 작업 범위와 저장소의 기존 검증·소유권 규칙을 적용한다.
