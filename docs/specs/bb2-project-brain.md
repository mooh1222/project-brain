## Problem Statement

Project Brain에는 현재 동작을 설명하는 개별 문서와 코드가 있지만, 객체의 종류·저장 위치·검색
노출·후보 검증·승격·스킬 권한·임시 지식의 수명주기를 한 번에 연결하는 실행 계약이 없다.
그 결과 긴 세션을 재개할 때마다 다음 네 상태가 섞였다.

| 상태 | 의미 | 이 명세에서의 취급 |
|---|---|---|
| 현재 구현 | 현재 커밋의 코드·테스트·CLI가 실제로 수행하는 동작 | 하위 호환 기준선 |
| dirty WIP | 작업 트리에 있으나 아직 검수·채택되지 않은 변경 | 먼저 별도 안정화할 선행 작업 |
| 합의·미구현 | 사용자가 방향을 승인했지만 통합 계약과 구현은 없는 설계 | 이 명세가 실행 계약으로 구체화 |
| 과거·대체됨 | 뒤의 결정으로 폐기되거나 좁혀진 안 | 재유입 금지 |

현재 production 기준선은 객체 19종과 설치 스킬 4종이다. 공통
`candidate.verification`, `GlossaryClassificationRecord`, 주제별 지식 초안은 아직 구현돼 있지
않다. 반면 작업 중인 query 문서는 단순 확인을 쓰기 승인으로 확대하지 말라고 하고, 같은 작업
묶음의 ingest 참고 문서는 사용자의 “맞다”를 즉시 승격으로 연결한다. 문서만 읽은 다음
에이전트는 어느 권한이 맞는지 재구성해야 한다.

어휘에도 같은 문제가 있다. 대표어·동의어·별칭이 같은 지식에 도달해야 한다는 합의와 달리
현재 검색 레인별 노출은 대칭이 아니다. 함수명이나 필드명 같은 코드 토큰을 실제 프로젝트
개념과 구분하는 공통 관문도 없고, 반복되는 문맥별 제외·별칭 판정을 정식으로 보존할 객체도
없다.

후보 승격은 더 직접적인 안전 문제다. 현재 수동 승격은 kind별 검증 신선도를 확인하지 않고,
자동 승격은 reviewed `DomainMapping`에 연결됐는지를 주된 자격으로 사용한다. 내용·근거·규칙·
실행이 바뀌면 검증을 무효화하고, 직접 reviewed 적재와 reviewed 의미 변경도 같은 검증을 거쳐야
한다는 합의가 아직 쓰기 관문의 공통 계약이 아니다.

또한 개발 중 여러 세션에 걸쳐 발견한 실제 표현, 확인된 사실, 가설, 충돌, 열린 질문을 정식
Brain 객체로 만들기 전에 안전하게 축적할 공간이 없다. raw 자료, candidate, dirty WIP의 비색인 pending 합성,
KnowledgePage는 각각 다른 역할이며 지식 초안을 대신하지 못한다. 임시 문서를 무심코 새 정본이나
검색 입력으로 만들면 “객체+근거가 정본”이라는 기존 설계를 깨뜨린다.

이 명세의 목표는 다음 세션이 전체 지도를 다시 만들지 않아도 되게 하는 것이다. 새 기능만
추가하는 것이 아니라 현재 19종의 역할과 새 계약의 위치, 기존 데이터의 읽기 호환, 쓰기 관문,
검색 노출, 네 스킬의 소유권, 문서 갱신 지점을 함께 고정한다. 이 명세는 목표 상태를 설명하며,
승인만으로 현재 구현이나 BB2 실코퍼스가 바뀌었다고 간주하지 않는다.

## Solution

### 1. 목표 상태와 전환 원칙

목표 상태는 정식 Brain 객체 20종과 설치 스킬 4종이다.

- 기존 19종은 읽기·검색 호환을 유지한다.
- `GlossaryClassificationRecord`만 20번째 정식 객체로 추가한다.
- `candidate.verification`은 candidate 내부의 검증 envelope이며 별도 객체가 아니다.
- 검증 준비 목록은 저장 객체가 아니라 현재 envelope에서 계산한 조회 결과다.
- 지식 초안은 config가 해석한 `<brain-root>/drafts/<topic-id>.md`에 존재하는 임시 작업공간이며
  Brain 객체가 아니다.
- `ObjectVerificationRecord`, `GlossaryQualificationRecord`, 별도 ready-list 객체, 다섯 번째
  설치 스킬은 만들지 않는다.
- 기존 객체는 새 필드가 없다는 이유로 로드·검색에서 탈락시키지 않는다. 새 candidate의 승격,
  새 reviewed 생성, 의미·근거가 달라지는 reviewed 갱신부터 새 계약을 강제한다.
- dirty WIP는 이 기능 구현과 섞지 않고 먼저 별도 검수 단위로 안정화한다.

검수하는 별도 ReviewRecord를 만들지 않는다.

`DomainContext`, `GlossaryTerm`, `DecisionRecord`, `DomainMapping`도 다음 세 조건이 모두 맞아야
query 확인 대상이 된다.

1. 현재 질문의 답이 그 후보의 의미·의도 선택에 따라 달라진다.
2. 현재 코드·문서·Brain 근거만으로 에이전트가 안전하게 풀 수 없다.
3. 확인을 받아도 그 답을 corpus 쓰기 승인으로 확대하지 않는다.

`candidate.verification`의 `needs_human`이나 열린 질문은 확인 필요성을 판단하는 강한 신호지만
필수 전제는 아니다. verification이 없는 후보도 위 조건을 만족하면 clarification 대상이 될 수 있다.

기술 근거, CodeLocator, 출처, 시간 사실, 색인·projection 같은 파생 객체의 검증은 query가
사용자에게 떠넘기지 않고 ingest 또는 해당 전용 갱신 경로가 맡는다.

### 3. 공통 candidate verification

#### 3.1 envelope

`common_verification` kind의 새 candidate는 공통 `candidate` metadata를 쓴다. 필수 필드는 기존
closed enum을 쓰는 `candidate_state`와 `candidate_source`, 생성 주체·시각인 `proposed_by`와
`proposed_at`, 정렬·중복 제거된 비어 있지 않은 문자열 배열 `open_questions`다.
`open_questions`는 질문이 없을 때 빈 배열이다. candidate의 의미를 만든 주체와 최종 검증자를
분리할 수 있도록 `proposed_by`는 실행 신원과 비교 가능한 안정 ID여야 한다.

기준선 schema에서 유효했던 모든 legacy candidate는 새 `proposed_by`, `proposed_at`,
`open_questions` 기본값이 없다는 이유만으로 로드를 실패시키지 않는다. 기존 GlossaryTerm에는
현재 필수인 `candidate_state`와 `candidate_source` 검사를 계속 적용하고, 다른 kind의 기존 후보에는
누락 진단만 낸다. 다음 의미 쓰기 때는 모두 공통 모양으로 올려야 한다. 기존
`candidate_state=ready_for_review`는 workflow 힌트일 뿐 아래 verification `ready`와 같은 뜻이
아니다.

승격 가능한 candidate는 선택적으로 `candidate.verification` v1을 가진다. 발견 직후에는
verification 없이 저장할 수 있지만 이 상태는 `unverified`이며 승격 준비 상태가 아니다.
envelope가 존재하면 아래 키와 형식을 정확히 만족해야 한다. candidate 경로에서는 sibling
candidate metadata와 envelope의 실행 복사본이 정확히 같아야 한다.

| 영역 | 필드 | 계약 |
|---|---|---|
| 버전 | `version` | 정수 `1` |
| 프로필 | `profile.id`, `profile.version` | kind별 검사 집합과 projection 규칙을 식별 |
| 결속 | `content_sha256` | candidate의 의미·검색 내용에 결속 |
| 결속 | `evidence_sha256` | 프로필이 선언한 직접 근거와 현재 source hash에 결속 |
| 결속 | `rules_sha256` | 프로필·필수 검사·권한·projection 규칙에 결속 |
| 결속 | `execution_sha256` | 실행 정보, 앞의 세 결속, 검사 결과, candidate state·열린 질문에 결속 |
| 검사 | `checks[]` | 안정적인 ID, outcome, authority, 비어 있지 않은 요약 |
| 실행 | `workflow`, `engine_sha`, `executed_at`, `producer`, `verifiers[]`, `subject_metadata` | 쓰기 경로, 실행한 코드와 시각, 의미 생산·검증 주체, candidate provenance |

top-level exact key 집합은 `version`, `profile`, `bindings`, `checks`, `execution`이다. `profile`은
`id`와 `version`, `bindings`는 위 네 SHA-256 필드만 가진다. 각 check는 `id`, `outcome`,
`authority`, `summary`만 가진다. `producer`와 각 verifier는 `kind`, `id`, `version`만 가지며
verifier가 둘 이상이면 `(kind, id, version)` 순으로 정렬한다. `workflow`는 `candidate`,
`direct_reviewed_create`, `reviewed_update`의 닫힌 enum이다. engine SHA는 40자 또는 64자 hex,
실행 시각은 timezone-aware ISO 8601이어야 한다.

`workflow=candidate`의 `subject_metadata`는 `candidate_state`, `candidate_source`, `proposed_by`,
`proposed_at`, `open_questions` exact key를 가지며 sibling candidate metadata와 byte-equivalent
canonical value여야 한다. 이때 `producer.id`는 `proposed_by`와 같아야 한다.
`direct_reviewed_create`와 `reviewed_update`에서는 `subject_metadata`가 JSON `null`이고 candidate
필드를 만들어내지 않는다. candidate promotion은 기존 `workflow=candidate` envelope를 다시
쓰지 않고 ReviewRecord로 옮기며 promotion origin은 ReviewRecord가 따로 결속한다.

검사 ID와 verifier는 정렬하고 중복을 금지한다. outcome은 `pass`, `fail`, `needs_human`만
허용하고 authority는 `agent`, `human`, `engine`만 허용한다. 각 kind profile은 필요한 검사와
허용 authority를 정확히 선언한다. `not_applicable` 결과를 저장하는 대신 프로필이 그 검사를
요구하지 않는다.

모든 profile v1은 다음 공통 검사를 정확히 포함한다. 아래 표에서 `E`는 engine, `A`는 agent,
`H`는 human authority이고 `/`는 그중 하나의 pass를 허용한다.

| 공통 check ID | 허용 authority |

경로도 ingest builder를 `producer`로 남겨 같은 독립성 규칙을 적용한다.

#### 3.2 네 결속 축

- verification은 기존 source 의미 해시 정본의 stable JSON·시각 제외 규칙과 ContextProjection의
  공식 projection/freshness 빌더를 재사용한다. 같은 의미를 별도 canonicalizer로 다시 정의하지
  않는다. 공유 해시 정본에 versioned named projection을 추가하고 verification도 그것만 호출한다.
- 내용 결속의 `verification-content-v1` projection은 lifecycle 시각, schema version, status,
  review ID, candidate metadata와 직접 근거 목록을 제외하고 나머지 의미·검색 필드를 해시한다.
  candidate에서 reviewed로 상태만 바뀌어도 깨지지 않지만 정의·범위·관계가 바뀌면 깨진다.
- 근거 결속은 프로필이 선언한 direct evidence pointer마다 pointer, object ID, 현재 **의미 내용
  hash** 또는 종류별 공식 external binding을 정렬해 해시한다. 파일 원문 hash를 무조건 쓰지 않아
  timestamp-only 변경으로 stale이 되게 하지 않는다. 무제한 재귀 대신 kind별 1-hop 입력을 선언해
  cycle과 과잉 무효화를 막는다.
- 규칙 결속은 profile ID와 버전, 필수 검사 집합, authority 정책, 내용·근거 projection 정의를
  해시한다.
- 실행 결속은 workflow·실행 신원·시각·producer·verifier·subject metadata, 앞의 세 해시,
  검사 결과를 함께 해시한다.

시간이 흘렀다는 이유만으로 stale로 만들지는 않는다. 현재성 검사가 의존하는 코드·원출처 hash나
검증 규칙이 달라질 때 stale이 된다.

#### 3.3 계산 상태와 사유 코드

`ready` boolean은 저장하지 않는다. 현재 store와 규칙으로 매번 다음을 모두 만족할 때만
`ready`를 계산한다.

- status가 candidate이고 capability 표에서 승격 가능한 kind다.
- envelope version과 profile이 지원된다.
- 내용·근거·규칙·실행 결속을 다시 계산한 값이 모두 같다.
- 필요한 검사 집합이 정확히 존재하고 모두 허용 authority의 `pass`다.
- 열린 질문과 conflict가 없다.
- 제안된 reviewed 모양이 schema와 lint를 통과한다.

계산 결과 필드 이름은 `verification_status`이며 기존 `candidate_state`를 대체하지 않는다.
진단 상태는 `ready`, `unverified`, `stale`, `blocked`로 제한한다. 기계가 반환하는 사유 코드는
다음 집합으로 고정한다.

- `verification_missing`
- `unsupported_version`
- `profile_mismatch`
- `content_changed`
- `evidence_changed`
- `rules_changed`
- `execution_invalid`
- `check_failed`
- `human_required`
- `open_questions`
- `kind_not_promotable`
- `candidate_conflict`
- `review_shape_invalid`

상태 매핑은 다음과 같다.

- 사유가 없으면 `ready`다.
- `verification_missing`만 있으면 `unverified`다.
- `unsupported_version`, `profile_mismatch`, `content_changed`, `evidence_changed`,
  `rules_changed` 중 하나가 있고 blocked 사유가 없으면 `stale`다.
- `kind_not_promotable`, `candidate_conflict`, `check_failed`, `human_required`,
  `open_questions`, `execution_invalid`, `review_shape_invalid` 중 하나라도 있으면 `blocked`다.

여러 사유는 `kind_not_promotable → candidate_conflict → check_failed → human_required →
open_questions → execution_invalid → review_shape_invalid → unsupported_version → profile_mismatch →
content_changed → evidence_changed → rules_changed → verification_missing` 순서로 반환한다.
`candidate_state=ready_for_review`만으로 verification `ready`가 되지 않으며,
`candidate_state=conflict`는 `candidate_conflict`를 만든다.

candidate의 의미나 근거를 바꾸는 쓰기는 fresh envelope를 함께 저장하거나 기존 verification을
제거해야 한다. 맞지 않는 이전 envelope를 그대로 둔 mutation은 거부한다. 수기 편집으로 생긴
불일치는 로드는 허용하되 query의 ready 목록에서 제외하고 audit에 경고한다.

#### 3.4 승격·직접 reviewed·reviewed 갱신

수동 승격과 자동 승격은 lock 안에서 live store 기준으로 envelope를 다시 계산한다. 성공 시
candidate의 normalized envelope를 `ReviewRecord.verification`으로 옮기고
`verification_origin=candidate_promotion`을 남긴다. 대상 객체의 의미·근거 projection은 검증된
candidate와 같아야 한다.

`common_verification` kind를 candidate 없이 reviewed로 만드는 경우 대상과 ReviewRecord를 같은
mutation에 요구하고 `verification_origin=direct_reviewed_create`를 남긴다. 기존 reviewed 객체의
의미·근거 projection이 달라지는 갱신도 새 envelope와 ReviewRecord 갱신을 같은 mutation에 묶고
`verification_origin=reviewed_update`를 남긴다. timestamp나 의미를 바꾸지 않는 기계적 참조
rewrite는 재검증 대상이 아니다. `dedicated_proof`와 `not_applicable` kind에는 이 규칙을
억지로 적용하지 않고 capability 표의 전용 증거를 검증한다.

ReviewRecord는 현재 verification만 덮어쓰고 과거를 Git commit 간격에 맡기지 않는다. 단일 target
ReviewRecord는 현재 `verification`과 append-only `verification_history[]`를 가진다. 의미 갱신 시
기존 normalized envelope, origin, 당시 target content hash, superseded 시각,
새 execution hash를 history에 먼저 보존한 뒤 현재 verification을 교체한다. history entry 수정·삭제는
금지한다.

단일 target의 exact 추가 key는 top-level `verification`, `verification_origin`,
`verification_history`다. 기존 top-level `reviewer`, `reviewed_at`, `verdict`는 current
verification에 적용한다. `verification_origin`은 `candidate_promotion`, `direct_reviewed_create`,
`reviewed_update`의 닫힌 enum이다. 각 history entry의 exact key는 `verification`,
`verification_origin`, `reviewer`, `reviewed_at`, `verdict`, `target_content_sha256`,
`superseded_at`, `superseded_by_execution_sha256`다. target content hash는 저장된 이전 envelope의
content binding과 같아야 하고 두 시각은 timezone-aware ISO 8601, execution hash는 64자 hex다.
history는 superseded 시각 오름차순이며 초기 검수에서는 빈 배열이다.

여러 DomainMapping을 한 bundle로 검수하는 현재 호환 경로는 `target_verifications[]`를 target ID로
정렬하고, 각 entry가 자기 current verification과 append-only history를 소유한다. 일부 target의
의미가 바뀌면 해당 entry만 재검증하되 bundle ReviewRecord를 같은 mutation에서 갱신한다. bundle의
상위 reviewer·reviewed_at·verdict는 “가장 최근 bundle record mutation”의 요약일 뿐 모든 target이
그 시각에 같은 verifier에게 재검수됐다는 증거로 사용하지 않는다. target별 envelope가 권위다.

각 bundle entry의 exact key는 `target_object_id`, `verification`, `verification_origin`, `reviewer`,
`reviewed_at`, `verdict`, `verification_history`다. history entry 모양은 single target과 같다.
top-level `target_object_ids`는 정렬된 bundle entry ID 집합과 정확히 같아야 한다. bundle에는
single-target top-level `verification`, `verification_origin`, `verification_history`를 금지한다.
반대로 single-target ReviewRecord에는 `target_verifications`를 금지한다. legacy ReviewRecord에는
새 key가 없어도 읽기를 허용하지만 새 검수·의미 변경부터 이 exact 모양을 요구한다.

대상과 ReviewRecord는 하나의 mutation manifest와 transaction으로 처리한다. 사전 검증 실패는
파일을 하나도 바꾸지 않고, apply 중 실패는 기존 journal recovery로 전체를 되돌린다. 별도
verification receipt 파일은 만들지 않는다. 기존 manifest의 대상별 after hash와 mutation receipt의
manifest hash·전후 corpus fingerprint가 결속의 정본이다.

#### 3.5 legacy 호환

- verification 없는 기존 candidate는 정상 로드되지만 `unverified`이고 승격할 수 없다.
- verification 없는 기존 reviewed와 ReviewRecord는 검색·조회에서 유지하며 소급 강등하지 않는다.
  audit에는 `legacy_unverified` 진단을 낼 수 있다.
- legacy reviewed의 의미·근거가 바뀌는 첫 쓰기부터 새 계약으로 업그레이드한다.
- 수기 신규 JSON과 진짜 legacy를 완전히 구별할 cutover inventory가 없는 v1에서는 missing
  verification을 load 오류가 아니라 감사 경고로 취급한다. mutation 경로의 새 쓰기는 예외 없이
  차단한다.

### 4. 공통 어휘 적재 계약

어휘 적재 기준은 지식 초안의 하위 규칙이 아니다. ingest, session-ingest, 직접 formalize,
migration이 모두 같은 독립 계약을 사용한다.

#### 4.1 GlossaryTerm 자격

GlossaryTerm은 실제 프로젝트에서 코드 토큰을 몰라도 독립적으로 질문하거나 설명할 가치가 있는
개념이다. 다음 검사를 모두 통과해야 한다.

1. 프로젝트 문서, 제품 화면, 팀 대화, 규칙 설명 등 코드 밖에서 실제 이름으로 쓰인 근거가 있다.
2. 함수·필드·enum·class 이름을 그대로 옮긴 것만은 아니다. 단, 코드 밖에서도 같은 이름이 실제
   개념으로 쓰이면 예외가 될 수 있다.
3. 다른 용어의 단순 속성이나 구현 세부가 아니라 독립된 정의와 경계를 가진다.
4. 너무 큰 주제나 지나치게 작은 토큰이 아니며, 필요한 경우 더 알맞은 kind로 분류한다.
5. 대표명, 정의, 포함·제외 범위, 소유 DomainContext가 분명하다.
6. 기존 GlossaryTerm과 같은 개념인지, 같은 표면만 공유하는 다른 개념인지 확인한다.
7. 반대 사례와 오분류 가능성을 일부러 찾는 adversarial check를 통과한다.

candidate GlossaryTerm도 “나중에 검토할 문자열 저장함”으로 쓰지 않는다. 후보 단계부터 실제 이름
근거, 독립 개념, 기본 크기 문턱을 통과해야 한다. reviewed 승격 때는 대표명·정의·범위·중복·소유
도메인까지 전체 검사를 다시 수행한다.

적재 스킬의 명부·자격 사전 대조는 제안 품질을 높이는 1차 관문이고, 모든 GlossaryTerm 생성·
변경이 합류하는 mutation vocabulary gate가 최종 권위다. 수기 JSON이 둘을 우회하면 audit가 같은
규칙을 전수 재실행한다. 최종 자격 검증자는 추출자와 분리하고 envelope의 producer·verifier
신원으로 이 독립성을 검증한다.

#### 4.2 대표어·동의어·별칭·교정 표현

- 대표어, 동의어, 별칭은 exact, scoped, lexical/vector, mapping, graph 경로에서 같은 지식에
  도달할 수 있어야 한다.
- 대표어는 답변 표시의 기본값일 뿐, 대표어로 match됐다는 이유로 더 높은 진실성이나 신뢰도를
  주지 않는다.
- 같은 표면이 여러 개념을 가리키면 domain, scope, 현재 질문 문맥, 근거로 해소한다. 그래도
  하나로 좁힐 수 없으면 임의의 필드 우선순위로 고르지 않고 모호성을 드러낸다.
- `GlossaryTerm.avoid`는 잘못되거나 피해야 할 표현을 대표어로 교정하기 위한 목록이다. 일반
  검색·graph 진입어가 아니며 avoid-only 질문은 대상 용어를 자동 회상시키지 않는다.
- 도메인 문서에서 용어 설명에 쓰는 `_Avoid_:` 표기는 문서 작성 시 피할 대체 표현을 뜻한다.
  데이터 필드 `GlossaryTerm.avoid`와 같은 기능으로 해석하지 않는다.

#### 4.3 GlossaryClassificationRecord

명백한 함수·필드·enum·class 토큰은 공통 규칙으로 제외하며 객체를 만들지 않는다. 다음 세션에도
반복될 문맥별 `exclude` 또는 `alias_to` 판정만 `GlossaryClassificationRecord`로 보존한다.

| 항목 | 계약 |
|---|---|
| truth role | `domain` |
| status | 신규 계약에서 `reviewed`만 허용 |
| 저장 | `objects/glossary_classifications` |
| ID | `gclass.<context-slug>.<surface-role>.<digest16>` |
| 유일성 | `(context_id, normalized_surface)`당 현재 객체 1개 |
| verdict | `exclude` 또는 `alias_to` |
| 검색 | 일반 FTS·vector·surface·query correction 제외 |
| graph | 참조 검증에는 포함하되 기본 graph export와 graph support에서 숨김 |
| snapshot | 정식 객체로 포함 |
| 조회 | 정확한 ID 조회, ingest 전용 keyed lookup, audit만 허용 |

`normalization_version` v1의 정확한 값은 `surface-v1`이다. normalizer는 입력에 Unicode NFKC,
Unicode default casefold, 앞뒤 공백 제거, 연속된 Unicode White_Space를 ASCII 공백 하나로 축약하는
순서를 적용한다. 구두점 제거, 한글 분해, 음역은 하지 않으며 결과가 비면 거부한다.
`surface-v1`은 Unicode 14.0.0 normalization·casefold table에 결속한다. 다른 runtime Unicode
version을 그대로 소비하지 않고 frozen table을 사용하거나 지원 불가로 실패한다.

`digest16`은 `context_id`, 위 normalizer가 만든 `normalized_surface`, `surface_role` 세 key의
canonical JSON SHA-256 앞 16자리다. ID의 context slug와 role, digest는 저장 필드에서 다시 계산해
검증한다. `<context-slug>`는 canonical DomainContext ID의 `context.` 뒤 slug이고,
`<surface-role>`은 저장 enum의 `_`를 `-`로 바꾼 값이다. digest 입력에는 변환 전 enum을 쓴다.
지원하지 않는 normalization version은 쓰기와 audit에서 실패한다.

필수 필드는 `context_id`, `surface`, `normalized_surface`, `normalization_version`,
`surface_role`, `meaning`, `verdict`, `reason`, 하나 이상의 `evidence_refs`다. `alias_to`에는
reviewed GlossaryTerm을 가리키는 `target_glossary_term_id`가 필수이고, `exclude`에는 이 필드를
금지한다. v1 `surface_role`은 `implementation_token`, `display_name`, `legacy_name`,
`local_shorthand`, `document_phrase`, `other_contextual`의 닫힌 enum이다.
v1 `alias_to`는 classification의 `context_id`와 target GlossaryTerm의 `context_id`가 같을 때만
허용한다. 현재 aliases가 target의 비문맥형 문자열 목록이고 classification 자체는 검색에서
제외되므로 cross-context alias를 “그 문맥에서만” 적용할 수 없기 때문이다. cross-context alias는
문맥별 검색 표면 계약을 별도로 승인하기 전까지 만들지 않는다.

같은 `(context_id, normalized_surface)`에서 surface role·meaning·verdict·target이 충돌하면 두
record를 만들거나 임의로 덮지 않고 `classification_key_conflict`로 실패해 사람 판단 입력으로
돌린다. surface role은 판정 이유를 설명하는 단일 현재 분류이며 logical key를 쪼개는 축이 아니다.
normalizer version을 바꾸면 ID와 logical key가 달라질 수 있으므로 별도 승인된 결정론적
delete+create·reference rewrite migration을 요구한다.

같은 logical key에서 이유·의미·근거·verdict·target이 바뀌면 precondition을 둔 reviewed 갱신을
한다. context·normalized surface·role이 바뀌면 새 ID가 필요하므로 원자적 delete+create로
처리한다. raw surface만 바뀌고 normalized surface가 같으면 같은 ID의 preconditioned update로
처리한다. 반대 근거가 생겼다는 이유만으로 표현을 전역 영구 차단하지 않고 현재 판정을 재검증한다.

`alias_to` 생성·갱신은 classification, 대상 GlossaryTerm의 aliases, 대상의 변경 검수 증거를
같은 mutation에서 바꾼다. target을 바꾸면 이전 aliases에서 제거하고 새 target aliases에 추가하는
것까지 원자적으로 수행한다. 반대 근거로 독립 GlossaryTerm이 되면 classification 제거,
검증된 새 용어 생성, 필요한 참조 rewrite를 승인된 migration 하나로 처리한다. rejected·archived·
superseded classification을 누적하지 않고 현재 판정과 Git·transaction 이력만 남긴다.

`alias_to`는 조건부로 `target_alias_value`와 `alias_ownership`도 요구한다. target aliases에
정규화 동등한 값이 정확히 하나 있으면 그 exact 문자열을 `target_alias_value`로 기록하고
ownership은 `preexisting`이다. 둘 이상이면 임의로 고르지 않고 `alias_surface_ambiguous`로
실패한다. 하나도 없으면 classification의 surface를 aliases에 추가하고 ownership은 `managed`다.
classification 삭제나 target 변경 때 `preexisting` alias는 자동 제거하지 않는다. `managed` alias는
같은 target·normalized surface를 지지하는 다른 live classification이 없을 때만 exact
`target_alias_value`를 제거한다. live classification과 target aliases가 어긋나면 조용히 고치지
않고 audit·mutation preflight에서 실패한다. `exclude`에는 target·alias ownership 필드를 모두
금지한다. 같은 target·normalized surface에서 role만 바꾸는 원자 delete+create는 기존 ownership과
target alias value를 그대로 이전한다. managed alias의 raw surface만 바뀌면 같은 mutation에서
이전 exact alias를 새 surface로 교체하고 ownership을 유지한다.

`alias_to` surface는 대상 `GlossaryTerm.aliases`의 공통 검색 표면 관문도 통과해야 한다. v1에서
현재 최소 길이·generic blocklist를 통과하지 못하는 1~2자 local shorthand는 alias_to로 저장하지
않고 draft의 사람 판단 항목으로 남기거나, 실제로 검색 별칭이 아니라는 근거가 있을 때만
`exclude`한다. 짧은 문맥별 exact alias 레인은 별도 호환성 설계 없이는 추가하지 않는다.

새 snapshot은 20-kind target registry를 가진 protocol v3로 만든다. v1·v2 snapshot은 버전별로
동결한 기존 19-kind target registry를 사용해 새 엔진에서도 verify할 수 있어야 한다. 현재와 같이
regular-file mode가 없는 v1 restore는 `snapshot_mode_unavailable`로 거부하고, v2만 restore
호환을 유지한다. v2 snapshot을 restore할 대상에 v3 전용 classification 파일이 하나라도 있으면
덮어쓰거나 남겨두지 않고 `legacy_snapshot_uncovered_targets`로 실패한다. 빈 복제 대상에는
19-kind 상태로 복원할 수 있다. draft, pending, backlog는 어느 snapshot version에도 넣지 않는다.

### 5. query 확인과 쓰기 승인

query 결과는 candidate 관련 출력을 세 가지로 분리한다.

- `candidate_object_ids`: 검색된 candidate 진단 목록
- `clarification_candidate_ids`: 현재 답에 꼭 필요한 사람의 의미·의도 확인 대상
- `ready_for_promotion_ids`: 현재 verification이 fresh하고 capability상 승격 가능한 목록

기존 `promotable_candidate_ids`는 이 명세에서 제거하지 않고 deprecated alias로 유지하되 의미를
`ready_for_promotion_ids`와 같게 만든다. 제거는 별도 호환성 명세와 사용자 승인 없이는 하지
않는다. 단순히 검색에 잡힌 candidate를 승격 가능하다고 부르지 않는다.

사용자의 “맞아”, “그 의미가 맞아” 같은 단순 확인은 현재 답의 모호성을 푸는 입력일 뿐 corpus,
index, Git을 바꾸는 승인이 아니다. “승격 준비로 검증해 둬” 같은 명시 요청은 candidate에 fresh
verification을 쓰고 candidate 상태를 유지한다. “바로 승격해 줘” 같은 명시 요청은 lock 안에서
재검증한 뒤 reviewed 객체와 ReviewRecord를 원자적으로 쓴다.

query는 명시적인 쓰기 의도를 판별하고 대상 ID와 현재 응답의 사용자 확인 근거를 ingest에
넘긴다. verification 저장과 승격 mutation은 ingest가 공개 ingest·promote 경계를 통해 수행하며
query가 직접 corpus를 쓰지 않는다.

`promote-auto` 명령명, 명시 ID 목록 입력, 기존 결과의 핵심 필드는 호환을 유지한다. v1 대상은
현재 호환 범위인 GlossaryTerm으로 고정하고, 선별 기준만 reviewed DomainMapping 연결에서 공통
`ready` 계산으로 바꾼다. 다른 kind의 자동 승격은 별도 결정 없이는 허용하지 않는다. mapping
연결은 진단 근거가 될 수 있지만 승격 자격은 아니다. verification 없는 legacy 후보, stale 후보,
비허용 kind는 고정 사유 코드와 함께 skip하고 자동 보강하지 않는다. 승격할 대상이 없으면 완전한
no-op이어야 한다.

### 6. 주제 소유 지식 초안

#### 6.1 역할과 파일 계약

지식 초안은 기능·도메인 주제가 소유하는 여러 작업 구간용 임시 작업공간이다. 세션, 티켓,
에이전트, agent-team은 참조일 뿐 소유자가 아니다. config가 해석한
`<brain-root>/drafts/<topic-id>.md`에 두며 파일이 존재하면 active이고, 모든 항목을 처리하면
삭제한다. 기본 폴더명이 `brain`이 아닌 소비 프로젝트도 같은 config 해석을 쓴다. completed 상태
파일이나 archive를 만들지 않는다.

`topic-id`는 파일명과 같은 불변 ASCII kebab-case다. 머리말은 다음을 가진다.

- schema version, topic ID, 제목, aliases
- 포함·제외 범위
- 알고 있는 context IDs와 관련 경로
- 선택적인 issue·ticket·session 참조
- 생성·최근 갱신 시각

초안 안의 모든 실질 주장과 질문은 안정적인 item 안에 둔다. 자유 서술에 지식을 숨겨 종료 검사에서
빠지게 하지 않는다.

v1 파일은 사람이 읽을 수 있지만 machine-owned인 canonical Markdown이다. 첫 줄은 title을 표시한
H1이고, 그 아래 `<!-- project-brain-draft:v1 -->` marker와 정확히 하나의 fenced JSON object만 둔다. JSON top-level key는
`schema_version`, `topic_id`, `title`, `aliases`, `scope`, `context_ids`, `related_paths`,
`work_refs`, `created_at`, `updated_at`, `sources`, `items`다. 다른 본문 서술은 허용하지 않는다.
직렬화는 UTF-8, LF, 마지막 newline, key 정렬, 2칸 들여쓰기, ID 기준 source·item 정렬을 사용하고
history 배열만 사건 순서를 보존한다. expected hash는 이 전체 file bytes의 SHA-256이다. 쓰기는
구조화 입력을 받는 draft CLI가 이 canonical form으로만 만든다.

#### 6.2 source와 item

초안 source는 정식 EvidenceRef가 아니라 나중에 재확인할 위치 정보다. exact 필드는 `source_id`,
`source_kind`, `locator`, `observed_at`, `content_binding`, `summary`다. `source_kind`는
`document`, `code`, `conversation`, `session`, `brain_object`, `external`의 닫힌 enum이다.
`content_binding`은 `binding_kind`와 `value`를 가지며 kind는 `git_sha`, `file_sha256`,
`object_source_sha256`, `message_id`, `url_etag`, `unbound` 중 하나다. `unbound`면 비어 있지 않은
`unbound_reason`을 추가로 요구한다. 기존 source 본문을 덮어쓰기보다 새 source ID를 추가한다.

각 item은 다음 계약을 가진다.

| 필드 | 의미 |
|---|---|
| `item_id` | 초안 안에서 불변인 ID |
| `knowledge_state` | `expression`, `confirmed`, `hypothesis`, `conflict`, `question` |
| `statement` | 현재 이해 또는 질문 |
| `source_links` | source와 세부 위치, supports·contradicts·mentions·user_confirms 관계 |
| `uncertainty` | 아직 불확실한 점 |
| `next_check` | 다음에 확인할 코드·문서·사람의 의도 |
| `route_hint` | 예상 kind나 종료 위치; 최종 분류가 아님 |
| `lifecycle` | `open`, `ready_to_route`, `routed`, `superseded` |
| `history` | 의미 변경의 append-only 이력 |
| `route_receipt` | terminal 상태에서만 존재 |

history entry의 exact 필드는 `at`, `actor`, `event`, `before_item_sha256`, `after_item_sha256`,
`reason`, `source_refs`다. 두 item hash는 순환을 막기 위해 `history` 배열을 제외한 canonical
item-state projection의 SHA-256이고, routed 상태에서는 `route_receipt`를 포함한다. event는
`created`, `corrected`, `contradicted`, `confirmed`, `split`, `routed`의 닫힌 enum이고 created
사건만 before hash에 `null`을 허용한다. 서로 다른 목적지로 가야 하는 item은 먼저 더 작은 자식
item으로 나눈다. 부모는 `superseded_by`를 가진 superseded 상태가 되고 모든 자식이 끝나야 완료로
센다.

초안 단계에서는 GlossaryTerm 여부나 최종 kind를 확정하지 않는다. 문서·현재 코드·기존 Brain으로
풀 수 없는 제품·팀의 의미와 의도만 사용자에게 묻는다.
`knowledge_state=confirmed`는 draft 안에서 source나 사용자 진술이 확인됐다는 뜻일 뿐 reviewed
Brain 지식이나 verification `ready`를 뜻하지 않는다.

#### 6.3 발견과 동시 수정

초안 발견은 일반 query가 아니라 metadata 전용 동작이다.

- 관련 active 초안이 0개면 짧은 작업은 초안 없이 진행할 수 있다. 여러 작업 구간에 걸쳐 이해·
  근거·질문이 바뀔 주제일 때만 새 초안을 만든다.
- 1개면 topic ID, aliases, context, 관련 경로와 현재 요청이 맞는지 확인하고 “진행 중 지식
  초안”임을 표시한 뒤 재개한다.
- 여러 개면 제목·범위·work refs만 보여주고 선택받는다. 명백히 여러 주제인 요청은 여러 초안을
  읽을 수 있지만 쓰기는 파일별로 분리한다.
- v1은 초안끼리 자동 병합하지 않는다. 중복 초안도 각 item을 허용 목적지로 처리해 닫는다.

최소 CLI는 metadata 목록, 구조 lint, create, expected-hash update, expected-hash close를 제공한다.
`<brain-root>/.brain-local/knowledge-drafts.lock` 전용 lock으로 쓰기를 직렬화하고, update와 close는 읽은 전체 파일의 SHA-256 precondition을
요구한다. hash가 달라지면 파일을 전혀 바꾸지 않고 최신 hash를 반환한다. symlink를 따라가지 않고
같은 디렉터리에서 원자 교체하며 여러 초안을 한 번에 자동 수정하지 않는다.

#### 6.4 정식화와 다섯 종료 경로

정식화는 draft lint, 원문·현재 코드·기존 Brain 재확인, 최소 item 분리, 목적지 쓰기, route receipt
기록, receipt 재검증, 완료 삭제 순서다. 목적지 쓰기와 초안 갱신을 코퍼스 transaction 하나로
위장하지 않는다. 목적지를 먼저 쓰고 안정적인 목적지 ID로 receipt를 복구할 수 있게 해 중단 뒤
중복 쓰기를 막는다.

모든 leaf item은 정확히 다음 다섯 경로 중 하나로 끝난다.

workspace 목적지는 config가 해석한 Brain root를 기준으로 한다. 개발 backlog는
`<brain-root>/backlog/development.md`, pending 합성은 `<brain-root>/pending/insights.md`다.
installer가 빈 파일을 미리 만들지는 않으며 첫 route가 필요할 때 생성한다.

| route | 허용 내용 | receipt의 목적지 정보 |
|---|---|---|
| `brain_objects` | 공통 어휘·verification 관문을 통과한 하나 이상의 정식 객체 | object ID, kind, written hash, mutation receipt |
| `development_backlog` | 지식이 아니라 구현해야 할 작업 | entry ID, entry hash, file hash, origin 정보 |
| `glossary_classification` | reviewed 문맥별 exclude·alias 판정 | object ID, written hash, mutation receipt |
| `pending_insight` | 재사용 가치가 있지만 아직 정식 객체가 될 수 없는 교차 주제 합성 | entry ID, entry hash, file hash, 원본 backlink |
| `discard` | 중복·오해·무가치·범위 밖 항목 | 이유, 결정 주체, source refs |

모든 receipt는 input item hash, routed 시각·행위자, 목적지별 안정 참조를 가진다. pending entry는
원본 draft 경로, topic ID, item ID, item hash를 backlink로 반드시 갖는다. 이 backlink와 양쪽
hash가 맞으면 해당 draft item은 처리 완료다. backlog도 결정적인 entry ID와 origin 정보를 써서
재시도 중복을 막는다.

pending과 backlog의 v1 entry ID는 각각
`pending.<topic-id>.<item-id>.<input-sha16>`,
`backlog.<topic-id>.<item-id>.<input-sha16>`이다. `input-sha16`은 route 직전 canonical item
SHA-256의 앞 16자리다. 같은 ID가 이미 있으면 새 entry를 만들지 않고 내용 hash와 origin을
대조해 기존 성공을 재사용하거나 충돌로 멈춘다.

두 destination 파일의 machine-owned entry는 `### <entry-id>` heading,
`<!-- project-brain-route:v1 -->` marker, 정확히 하나의 fenced canonical JSON object로 구성한다.
기존 사람 작성 prose와 인식하지 못한 block은 보존한다. 공통 필드는 `entry_id`,
`origin_draft_path`, `origin_topic_id`, `origin_item_id`, `origin_item_sha256`, `routed_at`,
`routed_by`, `source_locators`다. pending은 여기에 `synthesis`, `uncertainty`, `next_check`를,
backlog는 `task`, `rationale`, `acceptance_hint`를 요구한다. destination update도 expected file
hash와 원자 교체를 사용한다. draft receipt에는 canonical entry hash와 destination file의 after
hash를 남긴다.

close는 모든 leaf item이 다섯 route 중 하나로 끝났고, superseded 부모의 자식도 모두 끝났으며,
현재 목적지와 receipt·pending backlink가 유효할 때만 허용한다. 모든 route receipt를 포함한 현재
draft bytes가 HEAD에서 도달 가능한 committed blob과 정확히 같아야 하고, file-backed 목적지도
receipt가 가리키는 현재 bytes가 HEAD의 committed blob과 같아야 한다. 단순히 과거 commit이 한 번
있는 것으로는 부족하다. draft가 다르면 `draft_uncommitted`, 목적지가 다르면
`route_target_uncommitted`로 삭제를 거부한다. Brain root가 Git worktree 안에 없거나 HEAD blob을
해결할 수 없으면 `draft_git_unavailable`로 실패한다. 비교 대상은 index의 staged blob이 아니라
소비 repo의 `HEAD:<repo-relative-path>` bytes다. close 결과는 삭제 직전 draft blob ID를 반환해
origin path·item hash로 Git에서 다시 찾을 수 있게 한다. 자동 stage나 commit은 하지 않는다.
완료 후 archive, tombstone, 완료 명부를 만들지 않는다.

#### 6.5 비정본·비검색 불변 조건

지식 초안은 다음 어디에도 들어가지 않는다.

- 정식 kind 집합과 BrainStore load 결과
- raw source scanner와 EvidenceManifest·EvidenceRef 자동 생성
- FTS·vector·registry surface·graph support·일반 query
- corpus fingerprint와 index row
- Project Brain snapshot manifest·payload·restore
- 정식 candidate나 reviewed 객체의 자동 생성 근거

일반 corpus lint·audit와 draft lint는 별도 축이다. draft 오류를 corpus 손상으로 보고하지 않는다.
Git 미추적, 현재 bytes 미커밋, route target 미커밋은 작업 중 경고이고 close에서만 차단한다.

#### 6.6 기존 네 스킬의 소유권

| 스킬 | 지식 초안 관련 책임 | 금지 |
|---|---|---|
| query | 일반 질문에서는 초안을 읽지 않음; 명시 재개·개발 착수에서 metadata 발견; 선택된 초안은 진행 중 초안으로 표시 | 초안 쓰기, 단순 확인 뒤 corpus 쓰기 |
| session-ingest | 초안 생성·갱신·부분 인터뷰·복구·pending/backlog routing·close 조율 | 문서·코드로 풀 수 있는 질문을 사용자에게 떠넘기기 |
| ingest | 정식 Brain 객체와 GlossaryClassificationRecord formalize; 공통 어휘·verification·mutation receipt 소유 | 미검증 초안을 정식 근거로 간주 |
| audit | draft lint를 read-only 실행하고 corpus 감사와 별도 보고 | 자동 수정·routing·삭제 |

공통 지식 초안 reference 하나를 네 스킬이 공유한다. installer는 계속 네 스킬만 설치하고 빈 draft,
pending, backlog 파일이나 session-start hook을 미리 만들지 않는다. 첫 실제 필요 시 해당 workflow가
만든다.

### 7. living architecture와 문서 상태 원장

기존 architecture entry, runtime map, data contracts, change map은 유지하고 구현과 같은 변경에서
보강한다. 객체·store·surface·skill topology는 구조화된 계약에서 파생하거나 자동 대조한다.

어휘 판정, 후보 검증, query 권한, 지식 초안 정식화가 네 문서에 다시 흩어지지 않도록
`docs/architecture/workflow-map.md`를 추가한다. 이 문서는 다음 흐름을 한 화면에서 연결한다.

1. source 또는 대화에서 draft·candidate로 들어오는 경로
2. kind capability와 verification을 거쳐 reviewed가 되는 경로
3. 대표어·동의어·별칭·교정·classification의 검색 노출 차이
4. query의 read·clarification·explicit write 분기
5. draft의 다섯 종료 경로
6. migration과 rollback, live 승인 경계

각 관련 문서는 현재 구현, 승인됐지만 미구현, 과거·대체됨 상태를 명시한다. 구현 티켓은 코드만
바꾸고 끝낼 수 없으며 해당 architecture 지도, 데이터 계약, 스킬 reference, 구조 계약 테스트까지
같이 갱신해야 한다. 날짜별 spec·plan·report는 이유와 이력이고 현재 동작의 권위를 대신하지 않는다.

Task 18 display migration의 특수 보존·검증 흐름은 기존 runtime·data·change 지도에 유지한다. 새
workflow map은 그 흐름을 링크하되 일반 migration으로 흡수하거나 계약을 중복 정의하지 않는다.

### 8. 구현·migration 순서

1. **dirty WIP 안정화**: query no-write와 ingest의 “맞다→promote” 모순을 먼저 없애고, 기존
   query/audit/ingest/session runtime 변경을 독립 검수·테스트 단위로 닫는다.
2. **격리된 엔진 구현**: 전역 editable main이나 BB2를 건드리지 않는 별도 worktree·venv에서
   capability registry, verification, glossary 관문, classification, draft 계약을 TDD로 구현한다.
3. **합성 데이터와 설치본 검증**: 엔진, CLI transaction, query no-write, 네 스킬, installer,
   architecture 구조 계약을 합성 fixture로 닫는다.
4. **BB2 read-only audit**: 현재 GlossaryTerm을 keep, reclassify, merge, split, human으로만 분류하고
   같은 입력에서 같은 exact plan과 plan hash를 만든다. live 파일은 바꾸지 않는다. plan hash는
   기존 clock 이전 canonical unstamped intent에 결속하고 `executed_at`, reviewed 시각, transaction
   ID 같은 apply-time 값은 제외한다. apply가 시각을 한 번 찍고 receipt가 plan hash와 실제 output
   hash를 연결한다.
5. **승인 관문 1**: 사용자가 read-only 분류 decision ledger, 사람 판단 항목, exact migration
   plan을 승인한다.
6. **복제 BB2 rehearsal**: 승인된 plan만 복제본에 적용해 reference rewrite,
   classification+alias+remove 원자성, rebuild, audit, eval, 대표 query를 실행한다. apply 전 v3
   snapshot을 만들고, committed rehearsal의 rollback은 검증된 pre-snapshot restore로 고정한다.
   journal recovery는 미완료 transaction 복구에만 쓰고 inverse plan은 별도 계약 전까지 쓰지 않는다.
7. **승인 관문 2**: rehearsal 뒤 현재 live 입력을 다시 read-only로 fingerprint하고, object의
   reviewed·verification 시각과 verifier·engine 신원을 고정한 `apply_context`로 별도 live staging
   artifact를 만든다. 사용자는 rehearsal 결과, 이 artifact의 managed corpus byte-exact diff·
   expected after hash·회귀 결과를 검토하고 live 실행 권한 포함 여부를 명시한다. transaction ID와
   실제 commit 시각은 local journal·receipt metadata라 managed corpus byte diff에서 제외하되
   receipt가 staging artifact hash를 결속한다.
8. **live cutover**: 승인 관문 2가 live 실행을 명시적으로 허용한 경우에만 이 명세 밖의 별도
   실행 티켓에서 install, migration apply, index rebuild를 수행한다. live apply는 현재 fingerprint와
   verification freshness를 다시 확인한 뒤 승인된 apply context와 staged corpus bytes를 재생성 없이
   그대로 쓰며, 하나라도 달라지면 새 staging과 승인 관문 2로 돌아간다.

## User Stories

1. 새 세션의 에이전트로서 architecture entry 하나에서 현재 객체 수, 저장·검색 레인, 네 스킬,
   write 흐름을 찾아 전체 지도를 다시 만들지 않고 작업을 시작하고 싶다.
2. 유지보수자로서 현재 구현, dirty WIP, 승인·미구현 설계, 과거·대체안을 구분해 문서 초안을
   production 사실로 오해하지 않고 싶다.
3. 기존 소비자로서 verification과 새 분류 객체가 없는 19종 corpus를 업그레이드 뒤에도 그대로
   로드하고 query하고 싶다.
4. 운영자로서 기존 candidate에 verification이 없어도 읽을 수 있되 승격 준비로 추정되지는 않게
   하고 싶다.
5. 운영자로서 기존 reviewed 객체가 새 검증 필드가 없다는 이유로 검색에서 사라지거나 강등되지
   않게 하고 싶다.
6. 개발자로서 기존 reviewed 의미·근거를 처음 바꾸는 순간부터 새 검증 계약으로 안전하게
   업그레이드하고 싶다.
7. 스키마 유지보수자로서 kind, ID grammar, 저장 경로, capability, object template 집합의 drift를
   자동으로 발견하고 싶다.
8. 검색 유지보수자로서 kind의 검색 레인 선언과 실제 surface extractor가 다르면 테스트에서
   발견하고 싶다.
9. querying agent로서 reviewed와 candidate를 분리해 보고 저장 상태를 신뢰 상태로 오해하지 않고
   싶다.
10. querying agent로서 검색된 모든 candidate가 아니라 현재 답에 꼭 필요한 의미·의도 후보만
    사용자에게 확인하고 싶다.
11. 사용자로서 단순히 “맞아”라고 답했을 때 corpus, index, Git이 바뀌지 않기를 원한다.
12. 사용자로서 “승격 준비로 검증해 둬”라고 명시하면 candidate 상태를 유지한 채 최신 verification만
    저장되기를 원한다.
13. 사용자로서 “바로 승격해 줘”라고 명시하면 live store에서 재검증한 대상만 reviewed와
    ReviewRecord로 원자 처리되기를 원한다.
14. querying agent로서 기술 근거·CodeLocator·출처·파생 객체 문제를 의미 질문으로 위장해
    사용자에게 떠넘기지 않고 싶다.
15. ingest agent로서 기술 후보를 종류별 verifier와 전용 갱신 경로에서 처리하고 싶다.
16. 도구 소비자로서 candidate 진단, 사람 확인 대상, 실제 승격 준비 목록을 서로 다른 필드로 받고
    싶다.
17. 기존 CLI 사용자로서 `promote-auto` 명령·핵심 출력·GlossaryTerm 대상 범위는 유지하면서 더
    안전한 자격 기준을 쓰고 싶다.
18. 운영자로서 reviewed DomainMapping에 연결됐다는 이유만으로 legacy 후보가 자동 승격되지 않게
    하고 싶다.
19. 운영자로서 자동 승격 대상이 하나도 없으면 파일·index·receipt가 전혀 바뀌지 않게 하고 싶다.
20. 검수자로서 candidate 내용, 근거, 규칙, 실행 중 하나가 달라지면 ready가 사라지는 이유를
    고정된 코드로 확인하고 싶다.
21. 검수자로서 단순 시간 경과가 아니라 실제 의존 source나 규칙 변경이 있을 때만 stale이 되게
    하고 싶다.
22. 검수자로서 kind별 필수 검사와 허용 authority가 정확히 맞지 않으면 승격을 차단하고 싶다.
23. 검수자로서 열린 사람 질문이 하나라도 있으면 ready가 아닌 상태를 분명히 보고 싶다.
24. bulk 검증 사용자로서 한 후보의 실패가 다른 후보의 결과·신선도를 오염시키지 않게 하고 싶다.
25. 직접 reviewed 적재 사용자로서 common-verification kind는 candidate를 거치지 않아도 종류별
    검증과 ReviewRecord를 우회하지 않게 하고 싶다.
26. reviewed 수정 사용자로서 의미·근거 변경에는 새 검증이 필요하지만 timestamp나 기계적 reference
    rewrite에는 불필요한 재검증을 하지 않기를 원한다.
27. 감사자로서 수기 편집으로 낡은 envelope가 남아도 corpus 전체 로드를 깨지 않고 ready 제외와
    명확한 경고를 받고 싶다.
28. 복구 담당자로서 검증이나 review-pair 사전 검사 실패 시 파일이 하나도 바뀌지 않고, apply 중
    실패하면 transaction 전체가 복구되기를 원한다.
29. 도메인 작성자로서 모든 ingest·session·formalize 경로에서 같은 어휘 자격 규칙을 쓰고 싶다.
30. 도메인 작성자로서 실제 프로젝트에서 독립적으로 질문·설명할 가치가 있는 개념만
    GlossaryTerm으로 만들고 싶다.
31. 도메인 작성자로서 함수·필드·enum·class 토큰은 기본 제외하되 코드 밖 실제 개념 이름이라는
    근거가 있을 때만 예외를 허용하고 싶다.
32. 검수자로서 candidate GlossaryTerm도 발견 문자열 저장함이 되지 않게 최소 어휘 문턱을
    강제하고 싶다.
33. 검수자로서 reviewed GlossaryTerm의 종류, 크기, 정의, 경계, 대표명, 중복, 소유 도메인을
    확인하고 싶다.
34. 사용자로서 대표어, 동의어, 별칭 중 어느 표현으로 물어도 같은 지식에 도달하고 싶다.
35. 사용자로서 답변에는 대표어를 보되 대표어 match가 더 믿을 만하다는 잘못된 우선순위를
    적용받지 않기를 원한다.
36. 사용자로서 같은 표현이 여러 개념을 가리키면 문맥으로 좁히고, 끝내 모호하면 그 사실을
    답변에서 알고 싶다.
37. 사용자로서 avoid 표현을 썼을 때 올바른 대표어 교정은 받되 그 표현이 일반 검색 진입어가
    되지는 않기를 원한다.
38. 도메인 모델러로서 문서의 `_Avoid_:` 작성 표기와 데이터의 `GlossaryTerm.avoid`를 혼동하지
    않고 싶다.
39. ingest agent로서 명백한 코드 토큰 제외마다 불필요한 분류 객체를 만들지 않고 싶다.
40. ingest agent로서 다음 세션에도 반복될 문맥별 exclude·alias_to 판정만 정식 분류 객체로
    보존하고 싶다.
41. 감사자로서 같은 문맥·정규화 표현·표면 역할에 상충하는 현재 분류가 둘 생기지 않게 하고 싶다.
42. 도메인 유지보수자로서 반대 근거가 나타나면 전역 영구 차단 대신 현재 분류를 재검증하고
    재분류하고 싶다.
43. 도메인 유지보수자로서 alias_to를 만들거나 target을 바꿀 때 대상 aliases와 검수 증거가 같은
    mutation에서 함께 바뀌기를 원한다.
44. 검색 사용자로서 분류 기록이 일반 검색·기본 graph 결과를 오염시키지 않기를 원한다.
45. 감사자로서 분류 기록을 exact lookup, snapshot, lint, audit에서는 확인할 수 있기를 원한다.
46. migration 운영자로서 잘못된 GlossaryTerm의 의미·근거를 알맞은 kind에 보존하고 참조를
    고친 뒤 승인된 변경에서 제거하고 싶다.
47. 개발 에이전트로서 docs/raw가 있으면 그것에서, 없으면 사용자 대화와 현재 코드에서 주제 초안을
    시작하고 싶다.
48. 개발 에이전트로서 여러 세션에 걸쳐 실제 표현, 확인 사실, 가설, 충돌, 열린 질문, 변경·폐기
    이력을 구분해 갱신하고 싶다.
49. 사용자로서 문서·코드·기존 Brain으로 풀 수 있는 질문을 반복해서 받지 않고 제품·팀 의도만
    질문받고 싶다.
50. ingest agent로서 초안 단계에서 GlossaryTerm 여부나 최종 kind를 성급히 확정하지 않고 싶다.
51. 재개하는 에이전트로서 관련 active draft가 0개·1개·여러 개인 경우를 안전하게 발견하고
    선택하고 싶다.
52. 일반 query 사용자로서 관련 없는 지식 초안 목록이나 미검증 내용을 답변 근거로 보지 않기를
    원한다.
53. 개발 에이전트로서 session-start hook이나 agent-team 없이도 관련 작업 착수와 “이어서” 요청에서
    초안을 재개하고 싶다.
54. 협업 에이전트로서 다른 writer가 초안을 바꿨다면 expected hash 충돌로 멈추고 자동 병합하지
    않기를 원한다.
55. 운영자로서 draft가 raw, candidate, 정식 객체, query 근거, index, corpus fingerprint,
    snapshot에 들어가지 않게 하고 싶다.
56. ingest agent로서 formalize할 때 원문과 현재 코드를 다시 확인하고 공통 어휘·verification
    관문을 통과시키고 싶다.
57. 초안 유지보수자로서 각 leaf item을 정식 객체, 개발 backlog, 어휘 분류, pending 합성, discard
    중 정확히 하나로 닫고 싶다.
58. 초안 유지보수자로서 재사용 가능한 미검증 교차 주제 합성만 pending으로 보내고 원본 backlink와
    양방향 hash를 남기고 싶다.
59. 초안 유지보수자로서 목적지 쓰기 뒤 초안 receipt 기록이 중단돼도 결정적인 ID로 재개해 중복
    목적지를 만들지 않고 싶다.
60. 초안 유지보수자로서 미처리 item이나 깨진 receipt가 있으면 삭제를 거부하고 싶다.
61. 초안 유지보수자로서 모든 item이 끝나고 현재 draft·목적지 bytes가 Git에 보존됐음이 확인되면
    파일을 삭제하고 archive는 만들지 않고 싶다.
62. 스킬 사용자로서 query, ingest, session-ingest, audit이 같은 권한·용어·위임 계약을 안내받고
    싶다.
63. installer 사용자로서 기존 네 스킬만 설치되고 사용자 수정 파일이 보존되며 두 번째 설치가
    완전한 no-op이기를 원한다.
64. 감사 사용자로서 corpus audit와 draft workspace lint를 별도 상태로 보고 싶다.
65. 문서 유지보수자로서 구현 티켓마다 object/store/surface/skill/workflow 지도가 코드와 함께
    갱신되기를 원한다.
66. 문서 유지보수자로서 현재 코드에 이미 있는 drift와 이번 새 기능을 같은 완료 주장으로 섞지
    않고 싶다.
67. 구현 담당자로서 기존 dirty WIP를 먼저 독립 검수하고 새 verification 구현과 한 변경으로
    섞지 않고 싶다.
68. 구현 담당자로서 전역 editable main과 live BB2가 아닌 격리 worktree·venv에서 TDD로 개발하고
    싶다.
69. migration 운영자로서 live BB2를 바꾸지 않고 keep·reclassify·merge·split·human 분류와 exact
    plan을 반복 생성하고 싶다.
70. migration 운영자로서 같은 입력에서 같은 plan hash를 얻고 복제 BB2에서 reference rewrite,
    rebuild, audit, eval, query, rollback을 끝까지 검증하고 싶다.
71. 사용자로서 read-only 분류 ledger와 exact plan을 먼저 승인하고 싶다.
72. 사용자로서 복제 rehearsal과 live 직전 byte-exact diff·회귀를 다시 승인하기 전에는 install,
    migration apply, index rebuild가 실행되지 않기를 원한다.
73. 프로젝트 소유자로서 이 명세 승인과 코드 테스트 통과를 실제 BB2 content quality나 live parity
    완료로 오해하지 않고 싶다.
74. 프로젝트 소유자로서 기존 사용자 수정·미추적 파일이 이 작업의 stage·commit·cleanup 대상이
    되지 않기를 원한다.

## Implementation Decisions

1. **단일 capability registry**
   - 20종의 candidate 허용, query 확인, 직접 reviewed, 수동·자동 승격, 검색 레인, 전용 갱신,
     graph 노출, 검수 방식, ReviewRecord 정책을 한 registry가 소유한다.
   - schema, router, promote, mutation은 이 registry를 소비하며 각자 별도 allowlist를 재구성하지
     않는다.
   - 검색 surface의 kind별 extractor 구현은 분리하되 registry의 search lane과 정확히 대조한다.

2. **공통 verification 모듈**
   - envelope 생성, 현재 store에서의 상태 평가, candidate와 reviewed·ReviewRecord 쌍 검증을 한
     모듈이 소유한다.
   - readiness는 파생 값이고 저장된 수동 플래그가 아니다.
   - profile은 direct evidence projection과 종류별 검사·authority를 선언하며 무제한 참조 순회를
     하지 않는다.
   - 내용·근거 canonicalization은 기존 공유 의미 해시와 projection freshness 정본의 named
     projection을 재사용한다.

3. **legacy read/new write 비대칭**
   - optional envelope를 가진 legacy 객체는 읽는다. envelope가 있으면 exact v1 형식을 검사한다.
   - action-aware mutation gate가 common-verification kind의 승격, 새 reviewed, 의미·근거 reviewed
     갱신에 fresh verification을 강제하고 나머지는 capability의 dedicated proof를 강제한다.
   - 기존 객체 전체를 선행 migration하거나 소급 강등하지 않는다.

4. **ReviewRecord와 transaction 재사용**
   - 별도 검증 영수증 객체·파일을 추가하지 않는다.
   - common-verification kind의 promotion, direct reviewed create, meaningful reviewed update는
     대상과 현재 ReviewRecord를 한 transaction에 결속한다.
   - 현재 ReviewRecord는 최신 검수를 나타내고, 교체되는 normalized envelope는 target별 append-only
     history에 보존한다. Git·local transaction 이력만으로 portable 검수 이력을 주장하지 않는다.

5. **promote-auto 호환 전환**
   - 명령과 명시 ID 입력, 핵심 결과 필드는 유지한다.
   - v1 자동 승격 대상은 현재와 같이 GlossaryTerm으로 유지하고 fresh ready만 자격으로 쓰며
     mapping-vouched는 진단 신호로만 남긴다.
   - promotion 시점의 조용한 evidence backfill은 금지한다. 필요한 보강은 candidate 갱신과 재검증을
     먼저 거친다.

6. **독립 vocabulary gate**
   - draft 여부와 상관없이 모든 GlossaryTerm 생성·변경·migration이 같은 자격·표면·중복·소유
     도메인 검사를 사용한다.
   - 대표어는 출력 canonicalization이고 synonym·alias는 같은 검색 권한을 가진다.
   - avoid는 correction 전용이며 검색·graph surface에서 제외한다.

7. **GlossaryClassificationRecord는 정식 비색인 domain 객체**
   - reviewed 현재 판정만 보존하며 일반 검색과 기본 graph에서 숨긴다.
   - alias mutation은 classification, 대상 aliases, 검수 증거를 원자적으로 갱신한다.
   - 명백한 코드 토큰 제외에는 record를 만들지 않는다.
   - 새 snapshot protocol은 20-kind registry를 쓰고 legacy protocol은 동결된 19-kind registry로
     verify·restore한다.

8. **draft는 corpus 밖 구조화된 workspace**
   - 새 kind, 새 installed skill, raw source, KnowledgePage로 구현하지 않는다.
   - metadata·source·item·history·receipt 구조를 lint하고 expected-hash 쓰기로 충돌을 막는다.
   - 목적지와 draft receipt는 별도 transaction이며 결정적인 ID와 hash로 재시도를 idempotent하게
     만든다.
   - close는 현재 draft와 file-backed 목적지 bytes가 committed blob과 일치할 때만 허용한다.

9. **정확히 다섯 terminal route**
   - 정식 객체, 개발 backlog, 어휘 분류, pending 합성, discard 이외 경로는 허용하지 않는다.
   - pending은 reusable cross-topic unverified synthesis로 좁히고 source backlink와 receipt를
     완료 조건으로 둔다.
   - 완료 archive와 session-start hook은 만들지 않는다.

10. **네 스킬 유지**
    - query는 read와 clarification, session-ingest는 draft lifecycle, ingest는 formalization,
      audit은 read-only 진단을 맡는다.
    - 공통 reference를 공유하고 설치본 계약을 구조 테스트로 고정한다.

11. **living architecture를 구현 완료 조건으로 포함**
    - 기존 entry·runtime·data·change 지도는 유지하고 cross-cutting workflow map 하나를 추가한다.
    - 현재, 승인·미구현, 과거·대체 상태를 문서 metadata와 설명에 드러낸다.
    - kind/store/surface/skill topology와 문서 표를 코드 구조에서 자동 대조한다.

12. **dirty WIP와 새 기능 분리**
    - 기존 query·audit·ingest·session runtime 변경은 별도 review와 commit 단위다.
    - 특히 query no-write와 ingest의 단순 확인→promote 모순을 새 verification 구현 전에 닫는다.
    - 현재 알려진 문서·help drift는 기준선 안정화에서 처리하고 새 기능의 성공 근거로 세지 않는다.

13. **migration은 결정론적 plan 기반**
    - read-only audit은 keep, reclassify, merge, split, human만 출력한다.
    - exact input fingerprint와 clock 이전 unstamped plan hash, reference rewrite, evidence preservation,
      pre-snapshot restore rollback을 결속한다.
    - clone rehearsal과 두 사용자 승인 전에는 live install·apply·rebuild를 허용하지 않는다.

14. **사용자 상태 보존**
    - 자동 stage, commit, push, stash, 사용자 파일 정리는 하지 않는다.
    - installer는 사용자 수정 보존, 퇴역 관리 파일 처리, rollback, 두 번째 설치 no-op이라는 기존
      계약을 유지한다.

## Testing Decisions

### 1. 테스트 원칙과 선례

- 테스트는 public CLI·공개 응답·저장된 객체·receipt·파일 불변처럼 사용자가 관찰하는 동작을
  우선한다. 내부 helper 호출 순서나 private 함수 모양만 고정하는 테스트로 acceptance를 대신하지
  않는다.
- 현재 public mutation precondition과 journal recovery, query/router 출력, installer 사용자 수정
  보존과 2회 설치 idempotence 테스트를 선례로 삼는다. 새 helper 단위 테스트는 이 최고 경계를
  빠르게 진단하는 보조 수단이다.
- 실패 테스트는 결과 코드뿐 아니라 target·ReviewRecord·index·draft·Git 중 범위에 해당하는 상태가
  실제로 불변인지 확인한다.
- 결정론 테스트는 clock, random, embedder, tokenizer를 통제하고 plan hash와 canonical bytes를
  함께 비교한다.

### 2. 승인된 최고 경계

| 축 | 이번 명세의 최고 자동 검증 경계 | 이번 명세에서 하지 않는 것 |
|---|---|---|
| mutation | public CLI → mutation service → 저장된 transaction·ReviewRecord | live BB2 write |
| query | 실제 query 응답 필드와 단순 확인 전후 corpus·index·Git no-write | 사람 대상 광범위 사용성 조사 |
| draft·installer | 구조·충돌·route·삭제·비검색 자동 계약과 installer 2회 no-op | 임시 소비 프로젝트의 수동 다중 세션 pilot |
| migration | 복제 BB2 audit→plan→apply→rewrite→rebuild/audit/eval/query→rollback | live cutover |

이 네 seam은 이전 사용자 검토에서 이미 승인됐으므로 구현 티켓에서 다시 인터뷰하지 않는다.

### 3. 공통 verification과 mutation

- 기존 19-kind fixture를 verification 없이 load·query한다.
- legacy candidate는 `verification_missing`이며 ready·promote 대상이 아니다.
- legacy reviewed는 유지되고 의미 변경 때 새 계약으로 업그레이드된다.
- 내용·근거·규칙·실행 각 축을 하나씩 바꿔 stale 사유를 검증한다.
- unsupported version, profile mismatch, 누락·중복 check, 잘못된 authority, fail,
  needs-human, open questions, 비승격 kind를 각각 검증한다.
- 여러 후보의 bulk 검증 결과와 신선도가 독립인지 확인한다.
- candidate update가 fresh envelope를 함께 저장하거나 verification을 제거하는지 확인한다.
- 승격 시 reviewed와 ReviewRecord의 envelope·내용·근거 결속이 같은지 확인한다.
- direct reviewed 생성과 의미·근거 update가 검증을 우회하지 못하는지 확인한다.
- 의미를 바꾸지 않는 기계적 rewrite는 불필요한 재검증을 요구하지 않는지 확인한다.
- mapping bundle의 target별 verification과 부분 변경을 검증한다.
- 사전 실패 0-write와 apply 중 journal rollback을 public CLI 경계에서 확인한다.
- `promote-auto`의 fresh ready, stale, legacy mapping-vouched-only, 중복 ID, mixed 대상,
  no-eligible no-write와 호환 출력 키를 확인한다.
- 자동 승격 대상이 GlossaryTerm 밖으로 넓어지지 않는지 확인한다.
- 기존 candidate_state와 새 verification_status, 다중 reason code 순서를 각각 확인한다.
- candidate workflow의 subject metadata·producer equality와 direct reviewed workflow의 null metadata를
  확인한다.
- producer와 GlossaryTerm 최종 verifier 독립성을 확인한다.
- ReviewRecord의 단일 target·bundle target별 append-only verification history를 확인한다.
- single·bundle ReviewRecord의 exact key 상호배제, target ID 집합, history 정렬·hash 결속을
  확인한다.

### 4. 어휘와 분류 객체

- 실제 프로젝트 이름 사용 근거가 있는 독립 개념의 positive fixture를 둔다.
- 함수·필드·enum·class 토큰, 과대·과소 크기, 중복, owner 불명, 근거 없는 문자열의 negative
  fixture를 둔다.
- adversarial 반례가 GlossaryTerm 오적재를 막는지 확인한다.
- 대표어·동의어·별칭이 exact, scoped, lexical, vector, mapping, graph 레인에서 같은 지식에
  도달하는지 각각 확인한다.
- 같은 표면의 cross-context 결과가 문맥으로 좁혀지고 남은 ambiguity를 숨기지 않는지 확인한다.
- avoid-only 입력은 검색을 열지 않고 correction 표시만 하는지 확인한다.
- 분류 객체의 ID 재계산, field enum, evidence, target kind, tuple 유일성을 확인한다.
- 같은 표면의 role·verdict·target 충돌과 managed/preexisting alias ownership의 생성·보존·안전 제거를
  확인한다.
- surface-v1 NFKC·casefold·공백 축약과 collision fail, unsupported version을 확인한다.
- `alias_to` target 생성·변경·제거가 aliases와 ReviewRecord를 원자적으로 바꾸는지 확인한다.
- 현재 alias 표면 관문을 통과하지 못하는 짧은 local shorthand가 alias_to로 들어가지 않는지
  확인한다.
- 반대 근거 reclassification과 GlossaryTerm migration의 reference·evidence 보존을 확인한다.
- 분류 객체가 일반 search, correction, graph support, 기본 graph export에 없고 exact 조회·audit·
  snapshot에는 있는지 확인한다.
- 수기 JSON을 공통 glossary audit이 같은 규칙으로 잡는지 확인한다.
- v1·v2 19-kind snapshot verify, v1의 기존 `snapshot_mode_unavailable` restore 거부, v2 빈 대상
  restore, v3 20-kind snapshot, v2 restore 대상의 classification 잔존 fail-closed를 확인한다.

### 5. 지식 초안

- docs/raw 입력이 있는 생성과 사용자 대화+현재 코드만 있는 생성을 각각 검증한다.
- canonical Markdown marker·fenced JSON serialization, source, item, history, route receipt의 정상
  template과 malformed 입력을 검증한다.
- topic/path 불일치, 중복 ID, 끊긴 local ref, 허용되지 않은 상태·route를 거부한다.
- active draft 0개·1개·복수 발견과 metadata-only 반환을 검증한다.
- create 충돌, expected-hash update·close 충돌, symlink, 부분 쓰기 방지를 검증한다.
- item split과 superseded 부모·자식 완료 계산을 검증한다.
- 다섯 route별 필수 receipt와 목적지 존재를 검증한다.
- pending·backlog의 config 기반 목적지, managed entry 형식, 양방향 backlink·hash, 결정적 entry ID,
  재시도 중복 방지를 검증한다. 기본 폴더명이 `brain`이 아닌 config fixture도 둔다.
- 미처리 item, 깨진 receipt, Git 미추적, 현재 draft blob 미커밋, file-backed route target
  미커밋에서 close를 거부한다.
- 완료 삭제 뒤 Git으로 복구 가능하고 archive·tombstone이 생기지 않는지 확인한다.
- draft 수정 전후 store load, raw source 목록, corpus fingerprint, index row, query, graph,
  snapshot이 동일한지 확인한다.
- corpus audit와 draft lint 결과가 서로 다른 축으로 보고되는지 확인한다.

### 6. 스킬·installer·문서

- query, ingest, session-ingest, audit 네 template이 같은 권한 용어와 위임 계약으로 렌더되는지
  확인한다.
- query 설치본에 단순 확인 후 promote, projection write, index rebuild 같은 암묵 write가 없는지
  확인한다.
- session-ingest가 draft lifecycle을 소유하고 ingest가 formalize를 소유하는지 계약 테스트로
  확인한다.
- audit 기본 경로가 read-only이며 draft와 corpus 상태를 분리해 보고하는지 확인한다.
- installer가 사용자 수정 파일을 skip하고, 퇴역 관리 파일·실행 비트·rollback 계약을 유지하는지
  확인한다.
- 임시 대상에 두 번 설치해 두 번째 report의 created, updated, removed, adopted, skipped가 모두
  빈 배열인지 확인한다.
- kind, ID, store, capability, surface, template skill, architecture 표 집합이 정확히 맞는지 구조
  테스트로 확인한다.
- 새 세션의 독립 검토자가 architecture entry만 읽고 20종 역할, 검색 레인, 네 스킬, write·draft·
  migration 흐름과 상태 범례를 같은 말로 설명할 수 있는지 확인한다.

### 7. BB2 migration rehearsal

- read-only audit를 반복해 같은 input fingerprint, decision ledger, exact plan, plan hash를 얻는다.
- human 항목이 있으면 apply plan 생성을 fail-closed로 멈춘다.
- 복제본에서 keep·reclassify·merge·split별 object와 reference rewrite를 검증한다.
- classification+alias+remove, ReviewRecord 갱신, evidence 보존을 transaction 단위로 확인한다.
- apply 뒤 필요한 index rebuild, corpus checks, lint·audit, eval, 대표 query를 변경 축에 맞게 실행한다.
- plan hash가 apply 시각과 transaction ID에 영향받지 않고 stamped receipt가 같은 unstamped plan을
  가리키는지 확인한다.
- live staging의 고정 apply context로 계산한 managed corpus after bytes가 승인 뒤 live apply bytes와
  정확히 같고, local transaction metadata만 byte diff 밖에서 artifact hash에 결속되는지 확인한다.
- live fingerprint나 verification freshness가 승인 뒤 달라지면 apply가 0-write로 거부되고 새
  staging 승인을 요구하는지 확인한다.
- apply 전 v3 snapshot restore로 committed rehearsal을 rollback한 뒤 byte-level 원복과 동일한 query
  결과를 확인한다. journal recovery는 미완료 transaction에만 검증한다.
- live corpus에서는 이 테스트를 실행하지 않는다.

### 8. 결정론과 현재 baseline 해석

- 합성 엔진 테스트는 StubEmbedder와 정규식 tokenizer fallback을 사용하고 실모델에 의존하지
  않는다.
- 설치 runtime unittest와 전체 엔진 회귀를 모두 통과해야 한다.
- 이번 review 중 실행된 표적 `55 passed`는 dirty WIP의 현재 건강성 근거일 뿐, 이 명세의 새
  verification·분류 객체·draft가 구현됐다는 증거가 아니다.
- 과거 세션의 테스트 receipt는 “기록상 통과”로만 취급하며 구현 완료 판정에는 현재 checkout에서
  다시 실행한 결과만 쓴다.

- agent-team 의존성이나 지식 초안 전용 다섯 번째 설치 스킬

## Further Notes

- 명시적 사용자 승인 전에는 이 본문을 GitHub에 게시하거나 후속 ticket으로 분해하지 않는다.
- 게시 대상은 `mooh1222/project-brain` GitHub Issues이고 category/state는 정확히
  `enhancement` + `ready-for-agent`다.
- spec issue의 `ready-for-agent`는 승인된 child ticket 분해를 시작할 수 있다는 뜻이다. 이 큰
  issue를 한 번에 구현하라는 뜻도, live cutover 권한도 아니다.
- GitHub 원격 `main`은 현재 local `main`보다 뒤에 있으므로 게시 이슈 본문은 이 문서만으로 실행
  범위와 계약을 이해할 수 있게 자급자족해야 한다.
- spec 승인 뒤 research 원장의 `superseded_by`, 관련 ADR의 contract status, architecture entry와
  ROADMAP 상태를 실제 구현 단계에 맞춰 갱신한다. 승인 전에는 미구현 상태를 유지한다.
- 후속 `to-tickets`는 dirty WIP 안정화, 공통 capability·verification, 어휘·분류 객체, query·
  promotion, draft, 스킬·installer·architecture, BB2 read-only migration과 clone rehearsal을
  독립 티켓으로 나눠야 한다. live cutover 티켓은 두 승인 뒤에만 만든다.
- 현재 작업 트리에 있던 사용자 파일과 다른 WIP는 이 명세 작성 과정에서 정리·stage·commit하지
  않는다.
