# project-brain 공유 발표 읽기 자료

용도: 슬라이드를 넘기면서 그대로 읽거나, 한두 문장씩 줄여서 말하기 위한 발표자용 메모다. 전체 흐름은 10-12분 정도를 기준으로 잡았다.

## 1. Cover

**읽을 멘트**

오늘은 `project-brain`을 가볍게 공유하려고 합니다. 한마디로 말하면, 프로젝트 안에서 생기는 기억을 구조화해서 나중에 다시 꺼내 쓰는 엔진입니다.

여기서 기억이라고 부르는 건 문서만 말하는 게 아닙니다. 기획서, 코드, PR, 커밋, 슬랙 대화, 결정 이유처럼 프로젝트를 이해하는 데 필요한 조각들을 전부 포함합니다.

흐름은 단순합니다. 먼저 원문을 남기고, 그 원문에서 구조화된 객체를 만들고, 검색으로 필요한 조각을 찾고, 마지막에는 근거 있는 답으로 조립합니다.

**덧붙일 포인트**

- 이 자료는 제품 소개가 아니라 내부 공유용이다.
- 핵심은 "무엇을 저장하나"보다 "나중에 다시 믿고 꺼낼 수 있나"다.

## 2. 왜 필요한가

**읽을 멘트**

프로젝트 지식은 한곳에 모여 있지 않습니다. 어떤 건 코드에 있고, 어떤 건 기획서에 있고, 어떤 건 PR이나 커밋 메시지에 있고, 중요한 결정은 예전 대화 안에만 남아 있기도 합니다.

문제는 새 세션이나 새 사람이 들어왔을 때 같은 배경 설명을 계속 반복하게 된다는 점입니다. 더 위험한 건 애매하게 기억해서 그럴듯하지만 틀린 답을 만드는 경우입니다.

그래서 `project-brain`은 질문 시점에 필요한 조각만 근거와 함께 꺼내는 쪽을 목표로 합니다. 기록에 없으면 없다고 말할 수 있어야 안전합니다.

**덧붙일 포인트**

- "검색이 잘 된다"보다 "근거가 같이 나온다"가 중요하다.
- 프로젝트가 커질수록 기억보다 검증 가능한 기록이 더 안전하다.

## 3. 한 줄 정체성

**읽을 멘트**

`project-brain`은 사람이 직접 뒤지는 문서함이라기보다, 에이전트가 호출하는 프로젝트 지식 엔진에 가깝습니다.

질문은 사람이 합니다. 예를 들어 "이 용어가 정확히 뭐였지?", "이 매핑 아직 유효해?", "이 기능은 왜 이렇게 정했지?" 같은 질문입니다.

그다음 에이전트가 필요한 지식을 판단해서 `project-brain`을 호출합니다. `project-brain`은 관련 객체와 근거, 검수 상태를 돌려주고, 에이전트가 그걸 바탕으로 답을 만듭니다.

그래서 이 도구의 기본 전제는 답변이 근거와 검수 상태를 따라야 한다는 것입니다. 단순히 비슷한 문서를 찾는 것보다, 어떤 상태의 지식인지 같이 보는 게 핵심입니다.

**덧붙일 포인트**

- 사람이 매번 CLI를 외워서 쓰는 도구로 보면 방향이 조금 어긋난다.
- 에이전트가 프로젝트 기억을 회수할 때 쓰는 백엔드라고 보면 이해가 빠르다.

## 4. 저장 모델

**읽을 멘트**

저장 모델은 엔진과 데이터를 분리합니다. 이 저장소는 `project-brain` 엔진입니다. 스키마, 저장 로직, 색인, 검색, 라우터, 테스트가 여기에 있습니다.

반대로 실제 프로젝트 지식은 각 프로젝트 저장소의 `brain/` 디렉토리에 둡니다. 객체 JSON, raw 원문, 골든셋, 실측 가드가 그쪽에 있고, 프로젝트 git이 추적합니다.

중요한 점은 색인은 진실 원본이 아니라 파생물이라는 겁니다. `.brain-local/index.db` 같은 로컬 캐시는 JSON 원본에서 다시 만들 수 있습니다. 그래서 진짜 기록은 `brain/` 안의 원문과 객체 JSON입니다.

**덧붙일 포인트**

- 엔진은 공통으로 쓰고, 데이터는 프로젝트별로 가진다.
- 색인이 꼬이면 다시 만들면 된다. 원본 JSON과 raw가 더 중요하다.

## 5. 엔진 설계

**읽을 멘트**

엔진 내부는 원본에서 답변 후보까지 가는 얇은 파이프라인으로 보면 됩니다.

출발점은 `brain/` 아래의 객체 JSON과 raw 원문입니다. 이게 진짜 원본입니다. 저장할 때는 `schema.py`가 공통 필드와 타입별 필수 필드를 검사하고, `store.py`가 타입에 맞는 디렉토리에 씁니다.

그다음 `surface.py`가 타입별로 검색에 넣을 텍스트를 만듭니다. 같은 객체라도 용어, 매핑, 결정, 코드 위치는 검색에 노출해야 할 문장이 다릅니다.

색인은 `search_index.py`가 만듭니다. SQLite 안에 BM25용 FTS 색인과 vector 색인이 같이 들어갑니다. 여기서 색인은 원본이 아니라 재생성 가능한 캐시입니다.

검색할 때는 BM25와 vector 결과를 따로 뽑고, RRF로 순위를 합치고, 1-hop 그래프 연결로 서로 지지하는 결과를 올립니다. 마지막에는 router gate가 "검토된 답인지, 후보인지, raw 발췌인지, 없다고 봐야 하는지"를 가르는 역할을 합니다.

중요한 설계 철학은 코드가 의미 판단을 자동으로 대신하지 않는다는 겁니다. 코드는 저장, 색인, 검색, 상태 신호를 맡고, 어떤 지식을 어떻게 해석하고 검수할지는 에이전트와 운영 루틴이 맡습니다.

**덧붙일 포인트**

- `search_index.py`는 DB를 부분 갱신하기보다 전체 재구축하는 구조다.
- stale index를 막기 위해 코퍼스 지문이 맞지 않으면 검색이 거부된다.
- 이 구조 덕분에 "색인이 이상하면 rebuild"라는 단순한 운영 원칙이 가능하다.

## 6. 왜 타입이 나뉘는가

**읽을 멘트**

여기서 타입은 단순한 분류표가 아닙니다. "이 객체가 어떤 역할의 근거인가"를 나누는 경계입니다.

예를 들어 `EvidenceManifest`와 `EvidenceRef`는 원본과 원본 안의 특정 근거 위치를 다룹니다. `DomainContext`와 `GlossaryTerm`은 도메인 경계와 용어를 다룹니다.

`DomainMapping`은 조금 더 연결 역할에 가깝습니다. 어떤 도메인 의미가 어떤 용어, 결정, 코드와 이어지는지 한 지점에서 묶습니다.

`CodeLocator`는 구현 위치를 가리키고, `DecisionRecord`는 왜 그렇게 정했는지 남깁니다. `Insight`는 여러 객체를 가로지르는 교훈이나 위험을 담고, `ContextProjection`은 다음 작업에 다시 쓰기 좋은 브리핑을 담습니다.

타입을 나누는 이유는 각 타입마다 필요한 필드, 검증 규칙, 검색에 노출할 텍스트, 그래프 연결 방식이 다르기 때문입니다.

**덧붙일 포인트**

- 같은 "지식"이라도 원본, 용어, 결정, 코드 위치는 검증 방식이 다르다.
- 타입을 나누면 검색 결과를 더 안전하게 해석할 수 있다.

## 7. 실제 연결과 저장

**읽을 멘트**

객체들은 서로의 id를 필드에 담아서 연결됩니다. 이 id 필드들이 모이면 그래프가 됩니다.

예를 들어 `DomainMapping`은 중심에 놓기 좋은 타입입니다. `context_id`로 도메인 맥락을 가리키고, `glossary_term_ids`로 관련 용어를 묶고, `decision_record_ids`로 결정 기록을 연결하고, `code_locator_ids`로 코드 위치까지 이어줍니다.

여기에 `EvidenceRef`가 붙으면 이 매핑이 어떤 원문 근거에서 나온 것인지도 추적할 수 있습니다. 그래서 단순히 "이 말이 맞다"가 아니라 "어떤 근거에서, 어떤 코드와 결정으로 이어지는가"를 볼 수 있습니다.

저장할 때는 `schema.py`가 먼저 공통 필드와 타입별 필수 필드를 검사합니다. 그다음 `store.py`가 타입에 따라 `objects/domain`, `objects/mappings`, `objects/code`, `objects/decisions` 같은 디렉토리에 씁니다.

**덧붙일 포인트**

- `DomainMapping`은 용어, 의미, 결정, 코드가 만나는 접점이다.
- 검증을 통과해야 저장되기 때문에, 객체 타입은 실제 저장 규칙과 연결되어 있다.

## 8. 불러올 때 어떻게 쓰이나

**읽을 멘트**

불러올 때는 그냥 텍스트만 찾지 않습니다. 먼저 `surface.py`가 타입별로 검색에 넣을 텍스트 표면을 만듭니다.

그 위에서 키워드 검색과 의미 검색을 같이 씁니다. BM25는 토큰 기반 키워드 검색에 강하고, 벡터 검색은 표현이 조금 달라도 의미가 가까운 내용을 찾는 데 유리합니다.

그리고 여러 검색 신호를 합친 뒤, 그래프 연결도 같이 봅니다. 예를 들어 어떤 결과가 관련 용어, 결정 기록, 코드 위치와 함께 지지되면 더 신뢰할 만한 결과로 올릴 수 있습니다.

또 모든 것을 한 통로로 섞지 않습니다. 일반 객체, raw 원문, `Insight`, `ContextProjection`은 성격이 달라서 서로 다른 통로로 다룹니다. 그래야 검색 결과를 볼 때 "검토된 지식인지", "후보인지", "원문인지", "재사용 브리핑인지"를 구분할 수 있습니다.

**덧붙일 포인트**

- 검색은 "비슷한 문서 찾기"가 아니라 "상태와 연결까지 포함한 회수"다.
- raw, candidate, reviewed, projection을 섞어버리면 답의 신뢰도를 판단하기 어렵다.

## 9. 운영 흐름

**읽을 멘트**

운영 흐름은 근거를 보고 검수 상태를 정해서 쌓는 방식입니다.

먼저 구조화 노트를 만들고, `build` 단계에서 객체 묶음을 조립합니다. 이때 근거가 서면 객체는 곧바로 reviewed 상태로 만들어집니다. `ingest`는 그 상태를 그대로 검증·저장하고, reviewed에서 candidate로 후퇴하는 것만 막습니다. 즉 근거가 확실하면 사람 개입 없이 바로 reviewed로 들어갑니다.

candidate는 근거가 약하거나 충돌·검증 실패처럼 애매할 때 쓰는 예외 상태입니다. 이렇게 candidate로 남은 것을 나중에 확인해서 올릴 때 `promote`로 reviewed로 승격합니다. 이후에는 `search`나 `show`로 회수해서 씁니다.

이 흐름을 유지하려면 점검도 필요합니다. `audit`와 `lint`는 저장소 상태와 끊긴 참조를 보고, `graph isolated`는 아무도 가리키지 않는 고립 객체를 봅니다. `stale-check`는 코드가 바뀌어서 낡았을 수 있는 매핑을 찾아냅니다.

그래서 핵심은 많이 넣는 것이 아니라, 근거와 상태를 계속 유지하는 운영 루프를 만드는 것입니다.

**덧붙일 포인트**

- reviewed는 "근거가 서서 바로 쓸 수 있는 지식", candidate는 "근거가 약하거나 애매해서 아직 확정하지 않은 예외"로 보면 된다.
- 코드가 바뀌면 예전 매핑이 낡을 수 있으니 stale 확인이 필요하다.

## 10. 스킬로 에이전트가 쓰는 방식

**읽을 멘트**

여기서 중요한 부분이 스킬입니다. `project-brain`은 CLI만 있는 도구가 아니라, 프로젝트에 설치될 때 에이전트가 어떻게 써야 하는지도 같이 심습니다.

`project-brain install`을 실행하면 `.project-brain.json`이 만들어지고, 프로젝트의 `.agents/skills/` 아래에 brain 스킬 4종이 들어갑니다. 그리고 `.project-brain-manifest.json`이 어떤 파일을 도구가 심었는지 추적합니다.

첫 번째는 `brain-query`입니다. 도메인 질문이나 개발 착수 질문이 오면, 직접 코드를 뒤지기 전에 먼저 `project-brain search`와 `show`를 쓰게 합니다. 검색 결과가 없으면 brain에 없다고 말하고, 후보나 raw는 검수 상태를 붙여서 다루게 합니다.

두 번째는 `brain-ingest`입니다. 완료된 기능이나 이벤트를 나중에 소급해서 객체 그래프로 적재할 때 씁니다. 어떤 것을 `DomainMapping`, `GlossaryTerm`, `DecisionRecord`로 만들지 판단하는 건 에이전트의 일이고, 코드는 검증과 저장을 맡습니다.

세 번째는 `brain-session-ingest`입니다. 개발 중에 생긴 결정이나 과거 세션에서 뽑은 지식을 갱신할 때 씁니다. 네 번째는 `brain-audit`이고, lint, 고립 객체, stale-check 같은 코퍼스 건강 상태를 점검합니다.

즉 스킬은 "에이전트가 언제 찾고, 언제 저장하고, 언제 점검할지"를 고정하는 사용 설명서입니다. 엔진은 범용이고, 스킬은 그 엔진을 각 프로젝트에서 일관되게 쓰게 만드는 접점입니다.

**덧붙일 포인트**

- 스킬은 `SKILL.md` 하나만이 아니라 references와 scripts까지 디렉토리째 주입된다.
- 설치 후 사용자가 스킬을 프로젝트 어휘에 맞게 고치면, 다음 install이 그 수정을 함부로 덮지 않도록 manifest가 막는다.
- 그래서 project-brain은 "엔진 + 프로젝트별 코퍼스 + 에이전트 스킬" 세 층으로 보는 게 정확하다.

## 11. 같이 쓰려면

**읽을 멘트**

팀에서 같이 쓰려면 핵심은 많이 쌓는 게 아닙니다. 다시 쓸 수 있게 쌓는 것입니다.

새 지식을 남길 때는 raw 원문과 구조화 객체를 같이 남기는 편이 좋습니다. 그래야 나중에 객체만 보고도 근거를 따라갈 수 있습니다.

근거가 확실하면 바로 reviewed로 넣되, 근거가 약해 candidate로 남은 지식은 방치하지 말고 어떤 기준이면 reviewed로 올릴지 정해야 합니다. 반대로 아직 확정되지 않은 내용은 candidate로 표시되는 게 안전합니다.

그리고 팀 공유 전에는 권한, 검수 기준, 운영 루틴을 정해야 합니다. 누가 어떤 자료를 넣을 수 있는지, 어떤 기준이면 reviewed로 올릴지, stale-check나 audit를 언제 돌릴지 같은 부분입니다.

결론은 간단합니다. `project-brain`은 지식을 많이 쌓는 저장소라기보다, 근거와 검수 상태가 유지되는 프로젝트 기억 장치입니다. 이 상태가 유지될 때 에이전트가 프로젝트를 더 안전하게 도울 수 있습니다.

**덧붙일 포인트**

- 처음부터 완벽한 코퍼스를 만들려고 하지 않아도 된다.
