# 공통 어휘 판정 기준

이 문서는 모든 적재 경로가 `GlossaryTerm` 자격을 판단할 때 쓰는 단일 기준이다. 프로젝트에
등장한 문자열을 모으는 규칙이 아니라, 실제 프로젝트 이름과 단순 코드 토큰을 구분하는 규칙이다.
ingest·session-ingest·audit은 각자의 조건부 분기에서 이 파일을 읽고, 기준을 본문에 복사하지
않는다.

## 판정 순서

아래 질문을 순서대로 확인한다. 앞 단계에서 탈락한 표현을 뒤 단계의 `candidate`로 살리지 않는다.

1. **실제 이름 사용 근거가 있는가?** 사용자·팀 대화, 현행 기획·운영 문서, 화면 표기처럼 그
   표현을 개념의 이름으로 쓴 1차 근거가 있어야 한다. 코드에 식별자가 있다는 사실만으로는 명명
   근거가 되지 않는다. 코드명도 코드 밖에서 실제 이름으로 쓴 근거가 있으면 예외가 될 수 있다.
2. **독립 개념인가?** 그 표현의 뜻과 범위를 코드 구성요소 하나에 기대지 않고 질문하고 설명할
   수 있어야 한다. 구현이 바뀌어도 개념이 남고, 별도 이름이 있어야 다른 이름과 지식을 묶어
   회수할 가치가 있어야 한다.
3. **기존 어휘와 같은 개념인가?** 같은 개념의 `GlossaryTerm`이 있으면 새 객체를 만들지 않고
   대표어·동의어·별칭 가운데 알맞은 이름 역할로 연결한다. 철자가 다르다는 이유만으로 개념을
   나누지 않는다.
4. **크기가 적절한가?** 질문 가능한 상위 개념 하나를 잡는다. enum 값·필드·변수명마다 어휘나
   매핑을 하나씩 만들지 않는다. 반대로 서로 뜻과 범위가 다른 개념을 편의상 한 어휘로 합치지
   않는다.

## 코드 토큰과 비어휘 의미 라우팅

함수·클래스·enum·필드·변수명은 실제 공용 이름으로 쓰인 근거가 없으면 `GlossaryTerm`이 아니다.
제외한 뒤에도 남길 가치가 무엇인지에 따라 다음처럼 보낸다.

| 남길 가치 | 객체 선택 |
|---|---|
| 여러 코드 값이 함께 나타내는 질문 가능한 의미 | 값마다 객체를 만들지 않고 상위 의미 단위의 `DomainMapping` 하나로 묶는다. |
| 구현 파일·심볼·enum 선언 위치 | 해당 의미나 컨텍스트에 `CodeLocator`를 연결한다. 위치만으로 어휘를 만들지 않는다. |
| 재사용할 의미도, 따로 회수할 코드 위치도 없음 | 무객체로 둔다. 발견했다는 이유만으로 Brain 객체를 만들지 않는다. |

`DomainMapping`의 설명에는 값들의 역할과 변환 관계를 담을 수 있다. `CodeLocator`는 그 설명을
검증할 위치를 가리킬 뿐 의미 주장 자체를 대신하지 않는다.

## 대표어·동의어·별칭

- **대표어**는 같은 개념을 설명하고 답변에 표시할 기준 이름이다. 코드명보다 사람이 실제로 쓰는
  프로젝트 표현을 우선한다.
- **동의어**는 대표어와 뜻이 같은 자연어 표현이다.
- **별칭**은 옛 이름·화면 표기·내부 이름·실제로 이름처럼 쓰이는 코드 식별자다. 코드 식별자라는
  이유만으로 별칭이 되는 것은 아니다.
- 동의어와 별칭은 이름의 성격만 다르다. 어느 이름으로 질문해도 같은 어휘와 연결 지식에
  도달해야 하며, 한쪽에 더 낮은 검색 권한을 두지 않는다.
- `GlossaryTerm.avoid`는 대표어로 바로잡아야 할 교정 표현이다. 정식 검색 이름인 동의어·별칭과
  섞지 않는다.

같은 표현이 여러 개념에서 쓰이면 필드 종류만 보고 조용히 하나를 고르지 않는다. 도메인·범위·
명명 근거로 해소하고, 그래도 뜻이 갈리면 모호성을 드러낸다.

## `candidate GlossaryTerm` 최소 문턱

`candidate`는 “어휘인지 아직 모르겠다”는 대기함이 아니다. 다음 항목을 모두 만족해 어휘 종류와
대상이 정해졌지만 정의·근거·현재 유효성 일부가 아직 검수되지 않았을 때만 쓴다.

- 실제 이름 사용을 뒷받침하는 출처가 하나 이상 있다.
- 독립 개념이라는 잠정 정의와 범위를 쓸 수 있다.
- 소유 도메인과 대표어 후보가 정해져 있다.
- 기존 어휘와 같은 개념인지 검색했고, 남은 중복·충돌을 적었다.

이 문턱을 못 넘으면 `candidate GlossaryTerm`을 만들지 않는다. 입력 표현과 근거는 현재 작업의
초안·추출 기록에 보존하고, 비어휘 라우팅을 적용하거나 필요한 경우에만 사용자에게 묻는다.

## 에이전트 판단과 사용자 판단

에이전트는 1차 근거를 대조하고, 추출자와 분리된 검증으로 어휘 자격·크기·대표 이름·다른 이름·
중복·소유 도메인을 반박해 본다. 근거로 풀 수 있는 항목을 모두 사용자에게 떠넘기지 않는다.

다음 모호성만 사용자 판단으로 보낸다.

- 실제 팀에서 이름으로 쓰는지 끝내 확인할 수 없음
- 대표 이름 후보가 여럿이고 근거의 우선순위가 같음
- 한 개념으로 합칠지 서로 다른 개념으로 나눌지 결정할 근거가 부족함
- 현재 근거끼리 뜻이나 범위가 충돌함

사용자 판단 전에는 모호한 표현을 `reviewed`로 올리지 않는다. 사용자 확인을 받더라도 확인한
대상과 질문을 명시하고, 단순 확인을 다른 어휘나 승격 동작으로 넓히지 않는다.

## 바로 적용하는 정답과 반례

아래 판정은 표에 적힌 근거가 관찰된 경우의 결과다. 추가 근거가 생기면 같은 순서로 다시
판정하되, 코드 토큰이라는 사실만으로 결과를 뒤집지 않는다.

| 표현 | 관찰된 근거 | 판정과 라우팅 |
|---|---|---|
| `입장팝업` | 기획·화면·팀 대화에서 화면 이름으로 쓰이며 독립적으로 뜻과 범위를 설명할 수 있음 | `GlossaryTerm`의 대표어로 유지하거나 생성한다. 구현 위치는 별도 `CodeLocator`로 연결한다. |
| `OriginalPopup` | 클래스·파일 이름으로만 발견됐고 코드 밖의 이름 사용 근거가 없음 | `GlossaryTerm` 아님. 필요한 구현 위치만 `CodeLocator`로 연결한다. 실제 이름 사용 근거가 생기면 별도 어휘보다 `입장팝업`의 별칭인지 먼저 확인한다. |
| `카누 레이스 상태` | 기획·팀 대화에서 상태 체계의 이름으로 쓰이고 여러 상태를 묶는 독립 개념임 | `GlossaryTerm`으로 두고, 상태 값과 변환 의미는 상위 `DomainMapping` 하나에 설명한다. |
| `IDLE` | 카누 레이스 상태 enum의 한 값으로만 확인됨 | `GlossaryTerm` 아님. 값마다 객체를 만들지 않고 상태 체계 `DomainMapping`에 의미를 담고 선언 위치는 `CodeLocator`로 연결한다. |
| `RPMAP` | 재사용할 뜻이 확인되지 않은 변수·필드 식별자로만 발견됨 | `GlossaryTerm` 아님. 따로 회수할 의미나 위치가 없으므로 무객체로 둔다. 상위 동작의 의미가 확인되면 그 의미만 `DomainMapping`으로 다시 검토한다. |

감사에서는 기존 `reviewed GlossaryTerm`도 정답으로 가정하지 않는다. 위 기준으로 실제 어휘 유지,
코드 세부사항으로 재분류, 기존 어휘의 동의어·별칭으로 병합, 문맥별 분리, 사용자 판단이 필요한
모호성으로 나눠 읽기 전용으로 보고한다. 감사만으로 객체를 삭제하거나 수정하지 않는다.

이 기준은 `GlossaryClassificationRecord`, 공통 candidate verification, 기존 evidence
preparation의 공개 연결을 만들지 않는다. 판정 표나 작업 메모는 보고 근거일 뿐 새 Brain 객체가
아니다.
